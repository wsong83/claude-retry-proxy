## Summary

**Problem.** Every parse of untrusted JSON in the proxy is protected only by interpreter limits — and the *binding* one is not the one the first draft of this plan assumed. Measured on this host (Python 3.14.7, default recursion limit 1000): the json C decoder survives ~52,150 levels, the 3.12 env ~9,997 — but `_sanitize_schema_patterns` (the chat/response-mode tool-schema walker) recurses **one Python frame per schema level**, surviving only **997 levels at module level and failing at depth 1,000 with ~40 frames of call chain**. So a body whose tool schema nests ~955–1,000 levels would pass a 1,000-level limit check and then blow up *inside the transform*, where the total guard swallows it into a `transform_failure` event and forwards the **untransformed Anthropic body to an OpenAI endpoint** (chat/response modes) with no `nesting_limit_exceeded` and no path. The first draft of this plan (limit 1,000) had exactly that hole; the mega-audit found it and the limit is now **500** — ~2× below the walked-in-situ ceiling (≥450 frames of margin), ~20× below the json C ceiling, and still ~80× deeper than real traffic (~6 levels). Consequences of the original problem that remain: eight suite tests are calibrated against an interpreter profile that no longer exists; no document states what depth the proxy accepts; and `PROXY_MAX_BODY_SIZE` (10 MiB) does not bound depth at all (~5,000,000 levels fit under the cap).

**Approach.** Define the proxy's own limit — **500 nesting levels** — and enforce it by scanning the payload *before* every parse of untrusted JSON. The interpreter ceilings (both the json C ceilings and the Python-recursion walker ceiling) become unreachable by construction; the existing total-parse guards stay as defence-in-depth.

**Mechanism — the depth scanner (`nesting.py`).** `check_payload_nesting(raw: bytes | str)` is total on every input. For `bytes` it decodes via `json.detect_encoding(raw)` (falling back to `utf-8` with `errors="replace"`) so the scan sees exactly what `json.loads` will see; `str` is scanned directly. A C-speed fast path (`text.count("[") + text.count("{") <= limit` ⇒ pass, no scan) skips the scan for small payloads. The slow path walks the text with a string/escape state machine: brackets inside strings never count; a close at depth 0 is **ignored** (never pops an empty stack, never goes negative); every close pops the type stack blindly (a mismatched pair simply makes the repair parse fail later); the scan **early-exits at `limit + 1`**. `offset` is the index into the decoded text (character offset; equals the byte offset for ASCII payloads) — documented per site. Measured cost when the slow path runs: 13 ms at 0.29 MiB, 131 ms at 2.9 MiB, 420 ms at the 9.65 MiB cap (vs 4/46/158 ms for the `json.loads` the payload needs anyway); the deep case costs microseconds because of the early exit.

**Mechanism — the diagnostic (the 400's "which JSON").** On rejection the scanner knows the crossing offset and the types of the open containers on the way. Appending the matching close sequence to `text[:offset+1]` yields **valid JSON at exactly depth limit+1 (501)** — parseable safely on every supported interpreter (pyproject declares 3.8+; 501 ≪ any interpreter's recursion limit, and the proxy never raises the limit) — and walking that tree iteratively (explicit stack, no recursion) to the deepest node of the repaired prefix names the **first structure over the limit**. Components render as `.key` when the key matches `[A-Za-z_][A-Za-z0-9_]*`, else as `["<json-escaped key>"]`; the path is truncated to `path[:140] + "…" + path[-40:]` when longer than 200 characters. Prototyped 2026-10-25 against the live tree: a deep tool schema under `messages[0].content[1].input.schema` was located at that path prefix in 1.4 ms (the proto returned the full path; the wire form then applies the truncation rule above, so the client sees the head+tail form). Two bounded fallbacks: the repair is **skipped entirely** when the crossing offset exceeds 1 MiB (offset-only diagnostic), and any repair-parse failure degrades to `path: None` (offset-only diagnostic) — the offset is therefore always reported.

**The client-visible contract** (design confirmed 2026-10-25):

```json
{"type":"error",
 "error":{"type":"invalid_request_error","code":"nesting_limit_exceeded",
          "message":"Request body nesting depth exceeds the limit of 500 levels (first excess at offset 5105: $.messages[0].content[1].input.schema.a.a…)"},
 "request_id":"…"}
```

The path in that sample is **abbreviated for readability**: the wire form is exactly `path[:140] + "…" + path[-40:]`, so a real deep-chain path (~1,000 characters) always arrives as the 181-character head+tail form. When no path is available the parenthetical becomes `(first excess at offset 5105; body may not be valid JSON)`. The **admin** surface keeps its documented exclusion from the Anthropic envelope: the admin rejection is the admin surface's flat shape, `{"error": <message>, "code": "nesting_limit_exceeded"}` (admin.html's `errorText()` renders both shapes). The upstream direction never errors to the client: the payload is forwarded (or the frame skipped) unchanged, and a `nesting_limit_exceeded` trace event records `site`, `depth` (the crossing depth, `limit+1` — a lower bound), `offset` and `path` (`site` ∈ `request_body`, `admin_body`, `response_transform`, `response_rewrite`, `sse_first_event`, `chat_frame`, `compat_error_body`, `tool_args`, `response_body_capture`).

**Trust boundary:** the map covers every parse of *client- or upstream-derived* JSON. **Latent defect found while mapping:** `_chat_to_anthropic` (transforms_chat.py:585) and `_response_to_anthropic` (transforms_response.py:373) catch only `json.JSONDecodeError` around their `json.loads(args)`; a `RecursionError` from a deeply nested `arguments` **string** (invisible to any outer scan — it rides inside a JSON string) escapes them today, saved only by the caller's guard. Step 6 widens both to the total idiom.

**Alternatives considered and rejected:**
- *Keep 1,000 and make the schema walkers iterative* — removes the coupling but rewrites hot-path transform code; rejected by the user in favour of a 500 limit with a measured margin.
- *Re-fixture the eight tests against the running interpreter* — keeps the suite coupled to interpreter internals, defines no policy, and re-breaks on the next interpreter change.
- *Rely on the existing `RecursionError` guards alone* — protection varies by interpreter/version/shape and cannot be specified or tested deterministically.
- *Hand the offset to the client without a path* — rejected during design: an offset points but does not name; the repaired-prefix parse is the locator.

**Out of scope:** making the limit configurable (module constant, not an env var); capturing the offending body on the reject path (`--all` semantics unchanged apart from the site-9 fallback); capping non-JSON payloads; the three other open deferrals.

## Final Results

**Completed:** 2026-10-26
**Status:** COMPLETED

**What was built.** The proxy now enforces its own JSON nesting limit (`MAX_JSON_NESTING_DEPTH = 500`) before every parse of client- or upstream-derived JSON. A client or admin body nested deeper is rejected `400 invalid_request_error / nesting_limit_exceeded` (flat `{"error", "code"}` shape on the admin surface), whose message always names the crossing offset and names the offending JSON path when the locator can derive one. Upstream payloads — buffered bodies, SSE first events, chat frames, compatibility error bodies, tool-argument strings, the `--all` capture — are forwarded, skipped or degraded with a `nesting_limit_exceeded` trace event carrying `site`, `depth`, `offset` and `path`. Because the limit sits ~2× below the deepest nesting the proxy's own body walkers survive and ~80× above real traffic, the interpreter's json/recursion ceilings became unreachable by construction, which retired the eight interpreter-profile test failures the plan was adopted to fix.

**Steps.** All nineteen completed: Steps 1–7 (policy leaf, the client/admin/upstream enforcement sites, the test rewrite) by the coder and tester; Steps 8, 13 and 19 (documentation and its two deltas) by the planner; Steps 9 (stale comments), 10 (the client rejection's log-before-send ordering), 11 (node budget, `tier` fields, message split), 14 (the record walk and the `degrade` field), 16 (the byte-count fast path and `bytearray`) and 17 (the single-sourced event builder) by the coder; Steps 12, 15 and 18 (site coverage, the walk's verification and the fast-path/builder verification) by the tester.

**Test results.** `python3 tests/test_claude_proxy.py` → **475 passed / 0 failed / 475 total**, exit 0, on the planner's own final run and on the tester's three independent runs; the pre-plan baseline was 443 total with 8 interpreter-profile failures. Eighteen tests were added across the plan and three obsolete interpreter-profile probes plus their six helpers were retired. **Known caveats (all non-blocking; carried from the three reviews).**
- **The one item all three reviews raised and none closed:** the `nesting.py` module docstring's parenthetical still gives the pre-Step-14 reason for the node budget (the walk "would otherwise retain a path per element"; since Step 14 it retains one small record per node). It is the last stale statement in the file's contract text. Left unfixed deliberately at this point: it is a one-line comment in `src/`, which is the coder's lane, and reopening a fourth round for it would cost more than it is worth — it is a candidate for any future touch of that module.
- **`sanitize_error` bypass** (first review, Security): the client 400's trace entry carries its client-derived path in `error` without passing the documented chokepoint. Not a leak — the path reaches the trace by design through the event's `path` field — but inconsistent with every other request entry. Recorded, not fixed.
- **`_compat_guarded_parse` duplicate events**: it emits without `request_id`, and both matchers can run against one upstream body, so two identical uncorrelatable `compat_error_body` events are possible. The builder would make adding the field trivial now.
- **`chat_frame` and server-side `tool_args` omit `provider`** although it is in scope, so one site value (`tool_args`) has two shapes. `doc/trace-log.html` now states this plainly instead of claiming every site attaches what it has.
- **`nesting_event`'s `event.update(fields)` lets a caller overwrite a fixed field** (e.g. passing `path=` through the keyword bag) — demonstrated by the third review, no call site does it.
- **The sites gate's single-sourcing guarantee is weaker than its docstring**: it counts `nesting_event` calls without requiring the result to reach `log_trace`, and scans five hardcoded files with an exact expected total of 11, so a twelfth emitter in a *new* module would pass it. The tree is correct today.
- **The in-suite encoding differential is ASCII-only**, so the doc's "a bracket is a bracket byte in every encoding" claim is pinned by a probe rather than by the suite.

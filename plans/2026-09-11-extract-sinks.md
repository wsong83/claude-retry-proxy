*Issue notes:*

- *`sanitize_error`'s first regex arm backtracks exponentially.* Found by the iteration-2 mega-audit (2026-09-12, edge-case-explorer and security lenses independently) and re-measured by the planner using the pattern read out of the AST rather than retyped: `(?:/[^\s"]*)+` nests a `*` inside a `+` where both can consume `/`, so a whitespace-free run of slashes is partitioned ~2^n ways. Measured: 12 slashes 0.0002 s, 16 slashes 0.0028 s, 20 slashes 0.0446 s, 22 slashes 0.1797 s — ~4× per two characters, effective unboundedness near 40. This is reachable from **upstream-controlled** text: `sanitize_error` runs on the buffered body of a non-2xx upstream response (`server.py:4577`) and on the forwarding error paths (`:2251`, `:2262`). `ThreadingHTTPServer` gives each request its own thread, so one malformed upstream error body can pin a worker indefinitely — and `stop` does not drain in-flight requests, so nothing reclaims it. Pre-existing, and **frozen on purpose** by this plan: Step 1 asserts the moved body is byte-identical, which is exactly what makes the move reviewable. The extraction is also the cheapest prerequisite for fixing it — afterwards the function lives in a leaf module reached by the first test file that can call it directly. Filed as a deferred issue; see Risks.
- *`sanitize_error`'s path-redaction arm is inert on Windows.* Found 2026-09-12 while resolving the mega-audit's High finding on this function (see History). Measured, not inferred: the pattern `(?:/[^\s"]*)+([/\\]\.(?:claude|ssh|...))[^\s"]*` requires at least one **forward** slash, so a native Windows path — `[Errno 13] Permission denied: 'C:\Users\wsong\.claude\logs\proxy-trace.jsonl'` — passes through **completely unredacted**, while the same path with forward slashes is redacted. The IP arm and the 200-char truncation work on both platforms. This is the exact message class the sink failure path produces, and **no test anywhere in the repo references `sanitize_error`**, so nothing covers the behavior either way. Pre-existing and out of scope here: fixing the regex inside a verbatim move would destroy this plan's only reviewable property. Filed as a deferred issue. (It was also raised, and not fixed, by the previous plan's mega-audit — `tmp/reports/2026-09-10-guard-trace-state-sinks-mega-audit-2026-09-11.json:387-389`.)
- *`write_state` has no lock.* `write_state` differs from `log_trace` in taking no lock at all (`server.py:840-863`), and it writes through a **fixed** temp name (`STATE_FILE + ".tmp"`). Two concurrent writers — `heartbeat_loop` and `main()` are both callers — can truncate and interleave into that shared temp path before `os.replace` makes the swap. This is **pre-existing and out of scope** for a structural extraction: adding a lock would be a behavior change, and the class's shared write path makes it tempting "while we're here". Filed as a deferred issue; the plan does not touch it. See Risks.
- *`read_state` has zero callers and is deleted by this plan.* Exhaustive check on 2026-09-11 (whole repo, all file types): the only occurrence in `src/` is its own `def` at `server.py:832`. No `getattr` / `_hasattr` / `_require_server_func("read_state")` dynamic access exists anywhere. The three near-misses are not uses — `cli.py`'s `_read_state` (282) is an independent function reading the state file in the *CLI's* process, `tests/test_compat.py`'s `_read_state_file` reads the *compat* file, and `test_config_keys.py:284` names it only in a docstring explaining why the heartbeat must **not** use it.
  **Its only caller was removed by design, not by accident.** Plan `2026-08-26-fix-validation-direction-heartbeat` replaced `state = read_state()` with the in-memory `_startup_state` in `heartbeat_loop`, precisely because reading from disk returned `{}` after an external delete and corrupted the state file. Its Final Results record the heartbeat as "never reading from disk". The function was left behind with no caller. It is also already tracked as a deferred item: `plans/2026-09-10-guard-trace-state-sinks.md:317` lists "the `read_state()` dead-code hunch" among two items deferred by design.
  **No future need.** The split is intentional: the server owns state *writing*, the `cli.py` process owns *reading*. Nothing on the server side reads its own state file, and the admin API exposes config/providers, not state. Tests asserting a sink write can `json.load` the path directly. The one constructible future use — a shared state-file codec if `cli.py`'s duplicate is ever unified — is better served then by a purpose-built codec than by keeping a dead method alive now.
  **Consequence for the plan:** this is one of the plan's four module-surface changes (see Guidance for Coder). Removing a symbol is visible to any caller — there is none. This also resolves the `read_state()` hunch deferred by the 2026-09-10 plan; record it in `## Cross-References to Prior Plans` when `## Final Results` is written (Phase 6, step 4).

## Summary

**Problem.** `src/claude_retry_proxy/server.py` is 4,828 lines and holds six unrelated concerns. This plan extracts exactly one of them — the durable output sinks — as the first, smallest step of a staged decomposition. It is the first step because it touches **no** code in the retry loop, the streaming loops, or `do_POST`: every path constant it needs is read inside the sink functions themselves.

This plan follows `.claude/cluster-extraction-criteria.md` (mandated by the repo's `CLAUDE.md` "Refactoring" section): membership by the Concept/Substitution/Deletion tests, classes only where state has a lifecycle, first cluster chosen by blast radius rather than size, and one cluster per plan.

**Why the sinks, and why these four names.** The file contains two sinks, not the five things that sit in that region of `server.py`:

```
sanitize.py  __all__ = [sanitize_error]
             Shared leaf. NOT part of this cluster — see below.

sinks.py   __all__ = [TraceSink, StateSink, configure, log_trace, write_state,
                      increment_total, increment_retried,
                      write_start_marker, write_stop_marker]

_SinkHealth      the sinks' failure reporter. NOT a sink — a collaborator
                 they are given. Meaningless without them; nothing else uses it.
_Sink            private base — the concept.
                 write(payload) -> bool   [shared API, never raises]
                 Owns: _path, _name, _health, and the shared write path
├── TraceSink    append-only JSONL; + count_request(), count_retry(),
│                  start_marker(port), stop_marker()
└── StateSink    atomic replace of one JSON document

read_state is deleted, not moved (see Issue Log) — StateSink gains no read().
```

Membership test applied (delete the sinks — does it still make sense elsewhere?): `_SinkHealth` does not survive → member. `_BestEffortStderr` does → not a member. `_shutting_down` does → not a member. `_DISCONNECT_ERRORS` does → not a member. Counters and markers do not survive, because markers *are* trace entries and the counters exist only to feed the stop marker → they become `TraceSink` members. **`sanitize_error` survives intact** — four of its five callers are outside the sink cluster (`_load_compat_state`, `_forward_core` ×2, `ProxyHandler`) — so by the deletion test it is a shared leaf, not a sink member. It gets its own module rather than being dragged in.

**Lock topology.** The region holds **three** independent locks today, and the extraction reproduces all three. An earlier draft of this plan asserted a single lock and would silently have dropped two of them, degrading the health reporter's episode bookkeeping and the request counters.

| Lock | Owner | Ports | Guards |
|------|-------|-------|--------|
| `_SinkHealth._lock` | `_SinkHealth` | `_sink_warn_lock` (`server.py:747`) | the episode dict (`_sink_warn_state`), mutated from every worker thread and the heartbeat |
| `TraceSink._lock` | `TraceSink` | `_trace_lock` (`server.py:870`) | the JSONL append |
| `TraceSink._counter_lock` | `TraceSink` | `_request_counter_lock` (`server.py:873`) | `_requests_total` / `_requests_retried` |

`StateSink` owns none, matching today's lock-free `write_state`. The counter lock is **not** merged into the append lock: `increment_retried()` runs on the retry-storm hot path, and merging would make it queue behind JSONL file I/O. Marker methods must read the counters under `_counter_lock`, release it, and *then* write — mirroring `write_stop_marker`'s existing release-then-call at `server.py:940-943`. Holding the non-reentrant lock across `self.write()` would self-deadlock and hang process exit.

**Key design decisions.**

- **The base class is private (`_Sink`).** Nothing outside `sinks.py` subclasses it, so a public name would advertise a contract no one else honours. The shared policy is still testable through either concrete sink.
- **The shared write path is the one implementation change in this plan.** `write_state` and `log_trace` today carry the same skeleton — `if d:` guard → `makedirs` → write → POSIX `chmod 0o600` inside its own `try/except OSError` → `except Exception` → report → `False` / report-recovery → `True` — differing only in path and write mode. Both inner guards are load-bearing and must be reproduced: a relative sink path (`PROXY_STATE_FILE=proxy-state.json`, a documented behavior with a test at `tests/test_cli.py:1025-1050`) makes an unguarded `os.makedirs('')` raise, aborting startup and naming the wrong cause; and a chmod-only failure must not flip a successful write to `False`. That duplication is *why* the class family is warranted, not evidence *for* it; the justification is the shared concept and the shared `write(payload) -> bool` API. Collapsing it means one copy of a policy whose docstrings explain that an escaping `OSError` gets misread as a connection error and re-issues the upstream POST.
- **`sanitize_error` gets its own leaf module.** It is the redaction chokepoint for error text that reaches stderr, trace `error` fields, and the client-facing `upstream_unreachable` body — five call sites, four of them outside the sink cluster, and two prior artifacts already assigned it elsewhere (`tmp/plans/2026-09-07-break-up-large-files.md:82` puts it in `rewrites.py`; the criteria doc's §7 table lists it under *compat*). `sinks.py` may not import `server.py` (a module-level import resolves against a half-initialized module and raises `ImportError`), so the function moves to a true leaf — `sanitize.py`, importing only `re` — that both sides import. `server.py` keeps `sanitize_error` bound at module level via `from .sanitize import sanitize_error`, so its four remaining call sites are untouched. Moving it into `sinks.py` instead would make compat, forwarding and the handler import from the sink module.
- **The process-wide pair and `configure()`.** `sinks.py` holds one `TraceSink`, one `StateSink` and one shared `_SinkHealth`, and exposes `configure(*, trace_path=None, state_path=None, health=None)` to rebind them — `None` means "keep", and a rebuild reuses the shared health unless `health=` is passed. `server.py` calls `configure()` at import with the env-derived paths — mirroring today's import-time constants exactly — and `main()` calls it again after argparse, replacing today's `global PROXY_TRACE_FILE` rebind. This is deliberate: it preserves current behavior while removing the *path* from the write path, so nothing reads a module constant per write. Converting the 52 call sites to constructor injection is explicitly a later step's job.
- **`_SinkHealth` is shared, not per-sink.** Today one `_sink_warn_state` dict keyed by sink name (`"trace"`, `"state"`) and one lock serve both sinks. One shared instance reproduces that exactly, and gives tests a single object to construct with a fake clock. (Per-sink health would be observationally identical, since the keys are unique — but shared matches today's structure and is what the plan specifies.)
- **The delegates keep their names and signatures.** `log_trace(entry)`, `write_state(state)`, `increment_total()`, `increment_retried()`, `write_stop_marker()` are unchanged, so all 52 `log_trace` call sites and the other call sites need no edit — `server.py` just gains a `from .sinks import ...` line. **Two signatures/names change:** `write_start_marker()` becomes `write_start_marker(port)` (the port is data the sink has no business reaching for; one call site at `server.py:4781`, in the same coder step), and `read_state` is **deleted** (no caller anywhere — full evidence in the Issue Log).
- **`read_state` is deleted, and that plus the other three surface changes are the plan's only changes to the module name surface.** Relocation was the first instinct — a sink should be able to read what it writes, and relocation is mechanical where deletion is not. The exhaustive check reversed it: the function's only caller was removed by design in 2026-08-26, nothing reaches it dynamically, and the 2026-09-10 plan had already logged it as a deferred dead-code hunch. Keeping a dead method alive to preserve a symbol nobody references is speculative API (criteria doc §4).

**Alternatives considered and rejected.**

- *Extract the sinks as a module of plain functions* — would move the problem rather than solve it: `log_trace` and `write_state` each read a module-level path constant per call, which is precisely what `main()`'s `global PROXY_TRACE_FILE` rebind and the tests' path-swapping exploit. The path must be owned by something.
- *Include `_BestEffortStderr` because it shares the "must not raise" policy* — false cohesion. It is an adapter over someone else's stream with no path, no payload and no failure-reporting path; grouping on "similar policy" is the same pattern-similarity mistake that produces base classes nobody can unpick later.
- *Move `sanitize_error` into `sinks.py`* — mechanically simplest and wrong: four of its five callers are outside the sink cluster, so compat, forwarding and the handler would all end up importing from the sink module. The deletion test rules it out.
- *Inject `sanitize_error` into `_SinkHealth` as a callable* — pushes the problem to a default: either a duplicated regex (two copies of a security-relevant redactor) or a no-op that silently skips redaction for any directly-constructed sink. Moving it to a leaf has neither failure mode.
- *Fix `sanitize_error`'s Windows gap while moving it* — real defect, wrong vehicle: editing behavior inside a verbatim move destroys the one property that makes this plan reviewable. Filed as its own deferred issue.
- *Fix the `write_state` lock race while creating the class* — tempting, since the shared `_Sink.write` is exactly where a lock would go. Rejected: it is a behavior change inside a structural step, and it would make the one reviewable property of this plan ("nothing behaves differently") untrue.
- *Merge the counter lock into the append lock* — would take the lock count from three to two, but puts `increment_retried()` on the retry hot path behind JSONL disk I/O. Rejected; the three-lock topology is reproduced as-is.
- *Make the delegates disappear now (call sites use a sink instance)* — touches `do_POST` (1 site), `_forward_core` (2 sites) and all 52 trace sites. That is the risk zone this plan exists to avoid.

**Out of scope.** Every other cluster (`transforms`, `compat`, `settings`, `router`, `forwarder`, `admin`, `handler`); converting call sites to constructor injection; the `write_state` lock race; `sanitize_error`'s Windows redaction gap; `cli.py`'s independent and duplicated `PROXY_STATE_FILE` / `_read_state` / `PROXY_TRACE_FILE` (a different process's path resolution, deliberately not unified); `_BestEffortStderr`, `_shutting_down`, `_DISCONNECT_ERRORS`.

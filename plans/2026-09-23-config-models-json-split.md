## Summary

**Problem.** `~/.claude/proxy/config.json` currently carries two things that change on completely different schedules: the **tier mapping** (locally tuned, edited through the admin page) and the **provider model catalog** (imported from a shared repo). Because they share a file, any import of the catalog risks reverting the tuning — and this has already happened: `personal/proxy/config.json` in `claude-config` pins `tiers.opus` to provider `qwen` with model `deepseek-v4-pro-0813`, while the live file runs the same provider with model `deepseek-v4.1-flash`. In parallel, `claude-config` plan `2026-09-23-update-claude-env` has split its copy and ships a `bin/update-claude-env` that writes `personal/proxy/models.json` to `~/.claude/proxy/models.json`. **That file is inert until this repo learns to read it** — `load_config()` (`config.py:41-59`) hard-requires `models` inside `config.json` and raises otherwise, and there is no `models.json` concept anywhere in this repo today.

**Approach.** Split the document pair, keep the in-memory shape identical.

```
   ~/.claude/proxy/config.json          ~/.claude/proxy/models.json
   ───────────────────────────          ───────────────────────────
   tiers                       ─┐       models                       ─┐
                                │       extra_request_headers         │
                                │       disable_retry_claude_count_token
                                └──────────► merge ◄─────────────────┘
                                                │
                                     _current_config (in memory)
                                       tiers + models + extra_request_headers
                                         + disable_retry_claude_count_token
                                                │
                       ┌────────────────────────┼────────────────────────┐
                       ▼                        ▼                        ▼
              validate_config()        _resolve_extra_headers()   /admin/api/config
              (unchanged — it sees      (unchanged — reads the     (unchanged — returns
               the merged dict)          merged dict)               the merged dict)
```

**Merging at load and leaving every downstream consumer on the merged dict is the load-bearing decision.** `validate_config` is a direct-call target of 13 test sites (11 in `tests/test_config_keys.py`, 2 in `tests/test_retry_streaming.py`); keeping it a pure function of the merged dict means none of them move. The same is true of `_resolve_extra_request_headers` (`server.py:390`) and the `/admin/api/config` handler (`server.py:1988`).

**Contract:**

| Document | Keys | Required |
|----------|------|----------|
| `config.json` | `tiers` — and **nothing else** | `tiers` yes |
| `models.json` (sibling) | `models`, `extra_request_headers`, `disable_retry_claude_count_token` | `models` yes; headers and flag optional |

`config.json` holds the tier mapping and only the tier mapping. Everything that is *not* a tier mapping — the provider catalog, the header rules, and the count-tokens policy flag — lives in the sibling document, so the one file the admin page rewrites is the one file nothing else has an interest in. This also makes the count-tokens flag adoptable at runtime again: Reload Providers re-reads `models.json`, so a flag edit takes effect on reload rather than on a restart.

`models.json` is located as a **sibling of the resolved config path**, so `--config-path /tmp/x/config.json` reads `/tmp/x/models.json`. No new environment variable, and the existing suite's habit of redirecting `--config-path` into a temp dir buys test isolation for free.

**Four entry points change, and they are not all loaders:**

| Path | Site | Change |
|------|------|--------|
| Server startup | `server.py:2513` | via `load_config` — merges both documents |
| Admin reload | `server.py:2247` | **no longer calls `load_config`** — reads `models.json` only (Step 4) |
| CLI start / status | `cli.py:350`, `cli.py:696` | via `_load_config_for_validation` — merges both documents |
| Admin switch | `server.py:2210` | writes **tiers-only** to `config.json` |

**The clobber this plan exists to prevent, at the write path.** The admin hot-switch builds `new_config = {"tiers": new_tiers, "models": _current_config.get("models", {})}` plus preserved flags and calls `write_config(_config_path, new_config)` (`server.py:2198-2212`). Left alone, the first tier hot-switch after the migration would re-inject `models` and `extra_request_headers` into the freshly trimmed `config.json`, silently undoing the split on the live machine and recreating exactly the duplicate the split removes. Step 3 separates the disk document (`{"tiers": ...}` and nothing else) from the in-memory document (merged) at that call site.

**The admin page's two buttons are re-scoped, not just renamed** (user decision). Today `Apply` posts the tier mapping to `/admin/api/switch` and `Reload` re-reads the **whole** `config.json` from disk. After this plan:

- **Apply Config** → `/admin/api/switch` — applies the selected mapping and stores it in `config.json` (unchanged behavior, new label).
- **Reload Providers** → `/admin/api/reload` — reads **`models.json` only** and refreshes the available models. It **fails with 400 and performs no swap** if any currently-used tier's model is missing from the reloaded catalog.

This is a deliberate narrowing: reload stops picking up hand-edits to `config.json`'s tiers. The page needs no rework — `populateModels()` (`admin.html:133-152`) already rebuilds each dropdown from `config.models`, so re-rendering after a successful reload makes the refreshed catalog visible immediately. Without the server-side gate the failure mode is silent and worse than an error: `populateModels` restores the saved selection **only when the model is still in the list**, so a vanished model would quietly fall back to the first entry in the dropdown.

**Key design decisions:**

1. **`models.json` is mandatory; a leftover non-tiers key in `config.json` warns.** A missing `models.json` is a hard `ValueError` naming the path. Any of the three non-tiers keys (`models`, `extra_request_headers`, `disable_retry_claude_count_token`) still present in `config.json` is ignored with a one-line stderr warning naming the models file — it is not a source, and not an error. The leftover disappears on the next config write, since Step 3 makes that write exactly `{"tiers": ...}`. Keys outside the four-key contract entirely are dropped without a warning; see the out-of-scope note.
2. **The proxy never writes `models.json`** — with the single, existence-gated exception of first-install provisioning (`install_template`), which is the only place the file could be said to be "created by the proxy" at all. Every runtime write path is excluded, so a concurrent deploy and a hot-switch cannot race on the same file.
3. **Strictness lives in the loaders, not in `validate_config`.** One rule, enforced at the file boundary, keeping the validation function and its 13 direct-call sites untouched.
4. **The reload gate checks model membership, not just provider presence.** `validate_config` already requires a tier's provider to have a non-empty catalog entry; the new gate additionally requires the tier's **model** to appear in that entry. This is stricter than startup validation and deliberately so — see the out-of-scope note.
5. **The templates split too.** `src/templates/config.json` loses `models`, `extra_request_headers`, and `disable_retry_claude_count_token` to a new `src/templates/models.json`, and `install_template` writes both, so a fresh install starts on the new layout.

**Alternatives considered and rejected:**

- *Keep `models.json` optional, falling back to `config.json`'s catalog* — rejected by the user: two sources of truth is the ambiguity the split removes, and the fallback would silently mask a machine that never migrated.
- *Have the proxy write both files on every config write* — rejected: makes the proxy a second writer racing `update-claude-env`.
- *Enforce the model-membership rule in `validate_config` too* — rejected: it would convert currently-startable configs into startup failures and touch the direct-call test set, for a rule only the reload path was asked to enforce.
- *Rename `/admin/api/reload`'s endpoint to match the new button* — rejected: `claude-retry-proxy reload` and the page both call it, and the endpoint name is stable API surface; only the button label, the handler semantics, and the message text change.

**Explicitly out of scope:**

## Rollback

- **Steps 1–5 (all source + test changes):** `git revert` the plan's commit. Because the install is editable, reverted source reaches the CLI immediately and the live proxy on its next restart — no reinstall step, and no `~/bin/` copy to refresh (unlike `claude-config`'s deploy flow). **The commit does not exist yet** — it is created by `/update-and-commit` at the end of this plan, so until then "revert" means discarding the working-tree changes rather than reverting a commit.
- **Deviation as executed (2026-09-24): the `config.json.pre-split` backup was not taken.** Step 6 ran steps 2–4 only, so the checker's reconstruction test was **skipped, not passed** — there was no backup to compare against, and its `PASS` line reports the structural assertions alone. **Do not now manufacture the file by reconstructing it from the split pair**: that would make the test self-fulfilling and convert a skipped proof into a misleading one. Rollback is still available — the merged document is `{tiers} ∪ {models, extra_request_headers}` — but it is a reconstruction, not a preserved original. The pure move is nonetheless independently evidenced, which is why the deviation is recorded rather than treated as data loss: the live `tiers` match the values recorded **before any code changed**, the live catalog matches the repo's independent copy on both keys, `config.json`'s key set is exactly `{tiers}`, and the catalog still carries all 10 providers.
- **Step 6 (the live split) is the one non-revertable action, and it must be undone by hand.** It is deliberately reversible on its own terms: the step takes a `config.json.pre-split` backup, and the checker proves the pair reconstructs that backup exactly, so restoring the original is a single file copy. The order matters — **restore the backup first, then revert the code**, or the old code will reject the split config on the next start.
- **A partially completed migration** is safe to abandon: `config.json` is only ever written whole via `write_config`'s temp-file + `os.replace` path, so a half-written file cannot be observed. If only `models.json` was created and `config.json` was left merged, that state is fully valid under the new loader (the leftover catalog key warns and is ignored) — the migration can be finished later without a broken intermediate state.
- **A partial template install is self-repairing by construction — and, with Step 2's existence gates on both writes, non-destructive.** It writes `models.json` **first** and `config.json` **last** because `cmd_start` re-enters the install branch whenever either file is absent: a failed install leaves that signal in place, and the next `start` provisions only what is still missing instead of overwriting what is already there.
- **The reload gate is fail-safe:** a rejected reload performs no swap, so the running proxy keeps serving the previous catalog. There is nothing to roll back.

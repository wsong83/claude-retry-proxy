## Summary

**Problem.** The proxy is a drop-in replacement for the Anthropic Messages API — clients point `ANTHROPIC_BASE_URL` at it and expect Anthropic-shaped responses. Three things break that contract:

1. **Its error envelopes are non-standard.** Request-path rejections use a flat `{"error": "<string>"}`, where the standard puts an *object*. Operational failures use a near-standard nested shape but omit the top-level `"type": "error"` and `request_id`, and carry type names outside Anthropic's taxonomy.
2. **Two exception classes escape every client-body guard.** A body that is valid JSON but not an object (`null`, `123`, `[1,2]`…) raises `AttributeError` on `data.get(...)`; a deeply nested body (~16,912 levels, ≈34 KB) raises `RecursionError`. Neither is a `ValueError`, so no guard in the codebase catches them. The unguarded call at `do_POST:2750` runs *before* `forward_request`, so it pre-empts the entire downstream guard chain and the request aborts with **zero bytes** — no status line, no body, and no trace entry.
3. **One error path emits a status line no client can parse.** The unreachable-upstream branch returns status `0`, which renders as `HTTP/1.0 0 `.

**Approach.** One standard envelope builder, applied to the 13 proxy-generated error sites on the `/v1/*` path; the proxy's own diagnostics move into `error.code` so nothing is lost; the parse sites are made total; the two new shape errors get their own codes; and the malformed status-0 response becomes a real `502`.

**Key design decisions:**

- **`error.code` carries the proxy discriminator.** Anthropic's `error.type` is a coarse category; finer detail rides in `code`. This is observed, not invented — `compat.py:621` reads `code` from real upstream errors, and a real upstream SSE error frame in this repo's own trace carries `{"request_id":…, "code":"InvalidParameter", "message":…}`. The four existing proxy type strings become `code` values **verbatim**.
- **`request_id` is the proxy's per-request UUID**, placed in the standard top-level field. This is a **new extension** for the JSON envelopes — the design note that it was "already used in the SSE error frames" was **wrong** and is corrected here: the proxy's own SSE frame at `server.py:2223-2229` carries only `type`/`error.type`/`message` and no `request_id`, and it stays that way (frozen by the hard constraints). The cited precedent for `code` is the *upstream* SSE frame in the trace log, not the proxy's own. Its format (a UUID vs Anthropic's `req_…`) is not part of the schema contract.
- **The parse fix is local, not a shared helper.** Each site widens its own guard to catch `Exception`, matching `compat.py:633 _compat_guarded_parse` — the repo's existing canonical total-parse idiom, whose docstring already names `RecursionError`. A shared helper would have required a module-placement decision (the sites span three modules, and `compat.py` cannot import from `server.py`); the repo's refactoring doctrine governs module moves, so this plan keeps the change to one token per site.
- **`extract_model` returns a 2-tuple `(model_name, body_error)`.** The request path must distinguish "not valid JSON" from "not an object" to emit two different codes, and a string sentinel would collide with a client-supplied model named after the sentinel. No test calls `extract_model` directly, so the signature change is contained.
- **`_error_body` serializes with `json.dumps(...).encode("utf-8")`.** Two of the messages it carries are not static: `unrecognized_model` interpolates the **client-supplied** model name verbatim (`server.py:536-537`), and `upstream_unreachable` interpolates exception text. Today a call-site `json.dumps` guarantees escaping; moving that responsibility into a builder makes it explicit. A builder written with an f-string would emit malformed JSON or allow field injection from a model name containing `"` — and would pass every shape-only assertion, which is why Step 1's script tests escaping directly.

**Alternatives considered and rejected:**

- *Shared total-parse helper in a new module* — rejected: creates a module-placement decision that the repo's refactoring doctrine reserves for `/refactor-split`, for a saving of ~6 lines.
- *Keep the flat error shape but correct the message* — rejected: does not achieve protocol conformance, which is the point.
- *Adopt the nested `error` object but keep proxy type names as `error.type`* — rejected: `error.type` would then carry values outside Anthropic's taxonomy, and a client checking `type == "api_error"` would miss every proxy 500.
- *Add `error.param`* — rejected: genuinely applicable only to `unrecognized_model`; the other sites concern headers, paths and provider config, not body fields. Inventing `param` values would be worse than omitting the field.

**Explicitly out of scope:**

- The `/admin/*` error bodies — not an Anthropic surface. (`do_GET`'s *default* 404 is **not** in this group; see Step 5c.)
- The SSE error frame — already standard, and frozen.
- Upstream error bodies passed through verbatim on retry exhaustion.
- **Non-POST methods on `/v1/*`.** `PUT`/`DELETE`/`PATCH` fall through to `BaseHTTPRequestHandler`'s framework `501`, which returns an HTML body and bypasses the envelope entirely; the `method_not_allowed` site converted at `server.py:518` is only reachable for methods that reach `_forward_request_impl` at all. Giving those methods a per-method implementation is a feature, not a conformance fix, and no client in the trace log uses them. The `501` remains, and Step 4's gate is scoped to what it actually checks.
- Adding a broad outer `try` to `do_POST`. The `client-body-recursionerror` report explicitly argues against it (*"it would mask defects the current behaviour surfaces loudly in stderr"*), and this plan agrees — the choice is recorded here deliberately rather than left implicit.
- `do_POST`'s duplicate `extract_model` call. It remains, guarded, as the trace label's source.
- Any change to status codes other than Step 6's.

## Rollback

The change is confined to three source files — `server.py`, `compat.py`, `transforms_common.py` — plus the tests and doc surfaces that describe them. There is **no data migration, no persisted-state change, and no configuration change**: `feature-compatibility.json`, `config.json`, `models.json`, the keys file and the trace format are all untouched, and the CLI, env-var and admin-API surfaces are unchanged. Reverting is therefore a pure code revert, and no flag, dual-write or staged rollout is needed.

Each step lands as its own commit and no step leaves the tree in a non-building state, so any prefix of the sequence reverts cleanly; the plan's single consolidated commit reverts as a unit. The tests and docs revert with the code — reverting `server.py` alone would leave the rewritten assertions asserting a shape the code no longer emits, and the doc surfaces describing it.

The one behaviour a client could notice is the give-up path's `status 0 → 502`, and it is independent of everything else: Steps 1–5 (the envelope and parse totality) and Step 6 (the status) share no code, so if only the 502 proves problematic, revert Step 6 alone and keep the envelope work. The trigger to consider it is a client failing to parse the new envelope, or failing on the 502 where it previously tolerated the — unparseable — status-0 response; the trace log is the detection channel, since a request event carrying the new envelope alongside a client-side parse failure is the signature. The pre-change behaviour on that path was not a working baseline: the client received a response it could not parse at all.

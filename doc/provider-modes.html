Provider Modesanthropic, chat, and response — and what each one rewrites

Last updated: 2026-09-12

The proxy speaks Anthropic Messages to its clients. What it speaks upstream is configurable per provider, because not every provider implements the Anthropic API. A provider's mode decides the auth header, the upstream path, and how request and response bodies are translated.

ModeUpstream APIPathAuth header
anthropic Anthropic Messages the request's own path, unchanged x-api-key
chat OpenAI Chat Completions /v1/chat/completions Authorization: Bearer
response OpenAI Responses /v1/responses Authorization: Bearer

anthropic is the default: a provider entry with no mode field, or one whose value is empty, is treated as anthropic. Any other value draws a warning on stderr at startup — the proxy still starts — and requests through that provider then fail with 500 invalid_provider_mode. Because startup does not refuse, a bad mode is not caught until the first request reaches that provider.

Why this exists. Tier routing already lets you send a tier to a different provider. Modes are what let that provider be one that does not speak Anthropic at all — a self-hosted model, an OpenAI-compatible gateway, or a provider with an Anthropic-shaped surface but a different backend. The transforms are necessarily lossy in places; where they are, the proxy degrades visibly rather than silently (see Degradation).

Authentication and forwarded headers

The proxy is the only holder of the upstream credential. It never forwards the client's.

  • The client's authorization and x-api-key headers are discarded, unconditionally, in every mode.
  • The provider's credential is injected per mode: x-api-key: <key> for anthropic, Authorization: Bearer <key> for chat and response.
  • Only an allowlist of client headers is forwarded at all: content-type, anthropic-version, accept, anthropic-beta, and user-agent. Everything else the client sent is dropped.

Config-driven extra headers are applied after key injection and outside the retry loop, so an injected credential cannot be overwritten and a resolved header value stays stable across retries of the same request. See configuration.html.

Upstream paths

Anthropic mode forwards the request's own path, prefixed by whatever the provider's base URL contributes. The OpenAI-shaped modes ignore the incoming path entirely and substitute their own endpoint.

ModeResulting upstream path
anthropic<path_prefix> + <incoming path>
chat<path_prefix> (trailing /v1 removed) + /v1/chat/completions
response<path_prefix> (trailing /v1 removed) + /v1/responses

The trailing-/v1 removal is what stops a base URL that already ends in /v1 from producing a doubled /v1/v1/… prefix — the common case, since most OpenAI-compatible base URLs are documented with the /v1 included.

count_tokens is rejected in chat and response mode with a 400. The endpoint has no OpenAI equivalent, so there is nothing to translate it into. The check is tolerant of a trailing slash and a query string. Related: retrying count_tokens can be disabled separately — see configuration.html.

Request transforms

The outbound body is built once, before the retry loop, and is never rebuilt on a retry. A retry re-sends bytes; it does not re-transform them. The one exception is the compatibility retry described in Compatibility retry.

  • anthropic — the bare minimum: the model field is replaced with the provider's configured model name and everything else is passed through.
  • chat — the full Anthropic → Chat Completions transform (details).
  • response — the full Anthropic → Responses transform (details).

If a transform raises, the proxy falls back to sending the original body unchanged and records a transform_failure event — so a transform bug degrades to "upstream sees Anthropic-shaped JSON" rather than dropping the request. See Transform failures.

Response mode — request details

Response mode is buffered only: stream is forced to false on the outgoing request. There is no streaming path — see Streaming for what happens if the provider streams anyway.

The full conversation history is converted, in order, into Responses input items:

Anthropic inputBecomes
text, in a user / system / developer rolea message item with input_text
text, in a historical assistant turna message item with output_text
tool_use with valid argumentsa function_call
tool_resulta function_call_output — only when its tool_use_id matches a call that was actually emitted
tool definitionsflat Responses function tools (type, name, description, parameters)

The tool_result rule is an ordering constraint, not a formatting one: a result whose matching call was never emitted is dropped, because a dangling function_call_output is an upstream error rather than a recoverable one. tool_choice is likewise mapped only against tool names that were actually emitted.

Response rewriting

On success, the model name the provider returns is replaced with the tier name the client asked for, so a client tracking its own model selection sees what it sent rather than the provider's internal id.

ModeContent-TypeMechanism
anthropic application/json Parse, replace model, re-serialise
anthropic text/event-stream Buffer the first event (64 KB cap), rewrite model inside message_start, then forward that and every later event unchanged
chat / response any Full body transform — the rewrite falls out of the translation
any anything else Passed through untouched

Content-Type is checked first, before any buffering or parsing, so an unexpected content type is never parsed speculatively.

Error responses are not translated between formats. Chat and response modes pass a non-2xx response through byte-for-byte, so the client sees the provider's own error shape and wording. Anthropic mode is the one exception: it still applies its JSON model rewrite when an error body carries a top-level model field, so those bytes — and the model name reported in them — can change even on an error path. Not translating is deliberate: a translated error is harder to act on than an upstream one, and the proxy cannot know which error fields matter to the caller. It is also why the give-up path can promise the upstream's original body.

Chat mode — response details

An OpenAI Chat Completions body is converted back into Anthropic Messages. A reasoning_content field — or reasoning, which vLLM uses — becomes a thinking content block with an empty signature, inserted first in the content array, ahead of any text or tool-use blocks.

Response mode — response details

Every output item is inspected in order. message / output_text items become text blocks; function_call items become tool_use blocks, with arguments validated strictly (a dict is accepted, and {} is valid for a zero-argument tool).

stop_reason follows from what was actually emitted, which matters because the client uses it to decide whether to wait for a tool result:

Situationstop_reason
At least one valid function call was emitted"tool_use"
Calls were present but all degradednull
Completed without calls"end_turn"
Any other statusnull

The middle row is the important one: reporting "tool_use" with zero usable tool blocks would leave the client waiting for a result that can never arrive.

Streaming

Only the Anthropic-shaped path is a true stream. The other two modes differ sharply.

ModeStreaming behaviour
anthropic Upstream SSE is forwarded to the client, with the first message_start event's model rewritten in place.
chat Upstream OpenAI SSE is synthesised into Anthropic SSE frame by frame. This is a real streaming path — see below.
response stream: false is forced, so the normal path is a buffered JSON response. If a provider streams anyway, the stream is drained and a clean empty Anthropic terminal sequence is synthesised, with a response_sse_unexpected event. Raw OpenAI SSE is never leaked to the client.

Chat mode SSE synthesis

The converter assembles upstream frames on the \n\n delimiter (CRLF-normalised) and never splits mid-frame. [DONE] sentinels and non-data frames are skipped.

Two details shape the output:

  • The first content_block_start is deferred until the first delta's type is known. A reasoning_content / reasoning delta opens a thinking block at index 0; a content delta opens a text block. Opening the block eagerly would mean guessing, and guessing wrong would mis-number every later block.
  • Terminal events are emitted exactly once — on the finish_reason chunk, or synthesised at EOF or on truncation. An Anthropic client that never receives message_stop hangs, so the synthesis is unconditional.

Anthropic block indices come from a single monotonic allocator that is incremented only on content_block_start and never on close, which keeps indices contiguous even when tool blocks and text blocks interleave.

Tool calls

Tool-call translation is the most fragile part of every mode, because it is the only place where the proxy must parse model output it did not generate. Arguments arrive as a JSON string the model wrote, and models write invalid JSON.

Chat SSE tool-call bounds

Streaming tool calls arrive as fragments spread across many deltas, so the converter accumulates per-index state. Three bounds keep a misbehaving upstream from exhausting memory:

BoundValueApplies to
MAX_CHAT_TOOL_PENDING_BYTES64 KiBbuffered argument fragments per tool call
MAX_CHAT_TRACKED_TOOL_INDEXES32distinct tool-call indices tracked at once
MAX_CHAT_OPEN_TOOL_BLOCKS32Anthropic tool blocks left open simultaneously

Overflow in any of these does not error the stream. The affected tool call degrades, the rest of the stream continues, and the stream is reported once via a single bounded, metadata-only chat_sse_tool_degradation event. That event deliberately carries no tool names, ids, or arguments — only counts — so a degraded stream does not write model output into the trace log.

Malformed arguments

When tool-call arguments cannot be parsed as a JSON dict — a parse error, a non-dict result, an empty dict, a non-dict function value, or a non-dict tool-call entry — the proxy does not emit a tool_use block with empty input. Silently substituting {} would make a broken call look like a deliberate zero-argument call and could execute the wrong operation.

Instead it emits a visible text block naming the tool and call id, so the failure is legible in the transcript rather than invisible:

[Tool call failed: arguments for '<name>' (call <id>) could not be parsed as JSON]

A tool_args_parse_failure trace event is recorded alongside it.

When every tool call in a response is malformed, stop_reason is forced to null. This is the same hazard as the Responses-mode all-degraded case: a client seeing stop_reason: "tool_use" with zero tool_use blocks waits for a tool result that will never come, and hangs until it times out. Forcing null lets the client stop waiting and surface the placeholder text instead.

The request direction has the same problem in reverse: an input that is NaN, Infinity, or otherwise not json.dumps-serialisable cannot be sent. Those emit a placeholder reading … could not be serialized as JSON and a tool_args_parse_failure event. When a failed tool_use sits alongside valid ones in the same assistant message, the placeholder is emitted as a separate assistant message placed before the message carrying the tool_calls, so the ordering the upstream expects is preserved.

Transform failures

Both response transforms run inside a guard that treats a failed transform as "pass the original bytes through" rather than as an error. Crucially, the JSON parse happens inside that guard, so a body that is not JSON at all takes the same path as one that parses into an unexpected shape.

A transform_failure event is recorded — metadata only, never body content. The client receives the upstream's untransformed body. The trade is deliberate: for a chat-mode provider this means the client gets OpenAI-shaped JSON it may not understand, which is worse to debug than an Anthropic-shaped error but strictly better than a dropped response.

Compatibility retry

Anthropic mode has one extra behaviour layered over the retry loop. A single learnable feature (context_management) can be stripped from a request after an upstream rejects it, and the result learned per (provider, mode, model) so later requests strip it pre-emptively.

For this page, the relevant properties are:

  • It applies to anthropic mode only. Chat and response modes never run it.
  • count_tokens is excluded.
  • The compatibility retry is a single upstream attempt. The stripped variant is derived from the original client body with the feature field removed, and is re-sent through the normal forward path — one upstream attempt, but a fresh transform pass.
  • It runs under a single proxy-wide lock that allows at most one probe at a time; a request that cannot take the lock strips rather than probes.

The state machine, the probe ladder, and the suppression rules are documented in compatibility.html.

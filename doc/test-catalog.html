Running the suite

python tests/test_claude_proxy.py              # everything
python tests/test_claude_proxy.py -t <name>    # one or more named tests

tests/test_claude_proxy.py is an aggregator, not a test module. It imports each area module's ALL_TESTS list and concatenates them in historical section order into one run. Adding a test means adding it to its module's ALL_TESTS; the aggregator needs no edit unless you add a whole new module.

The suite is safe to run alongside a live proxy. This was not always true. The harness redirects the state, compatibility, and trace paths into isolated temp files at import time — the state path per-run, the other two session-scoped — so a test run cannot touch a running proxy's files. See Isolation.

Isolation

The suite's central correctness property is that it never touches real user state. This is achieved by setting environment variables before any server or CLI module is imported, because those modules read their paths at import time.

VariableRedirected to
PROXY_TRACE_FILEa session temp file
PROXY_STATE_FILEa per-run temp file (see below)
PROXY_FEATURE_COMPAT_FILEa session temp file

PROXY_STATE_FILE is the one path that needs more than a redirect. It is set to ~/.claude/proxy/claude-retry-proxy-test-state-<runner-pid>.json — the live proxy's own directory, but under a distinct name — keyed to the runner process, not a fixed machine-global name — and the harness removes any file at that path at import. That closes the failure mode a fixed name created: a dead proxy's PID survived across runs, and because Windows recycles PID numbers aggressively, start's is_pid_alive() gate could report an unrelated live process as Proxy already running and refuse to start. The path stays identical for the whole run — the harness, every spawned CLI subprocess and every spawned server inherit it through os.environ.copy() — and run_cli's per-test loop removes the file after every test, so no test inherits one left by an earlier test (neither the wrapper cleanup() closures nor a direct _start_proxy_server_directly spawn is relied on for this; a direct spawn's file is written by the server child, and on Windows terminate() is TerminateProcess, which runs no Python cleanup). A completed run therefore leaves nothing behind; a run that is hard-killed can still orphan its own file, since no cleanup can run. Those orphans are inert — the next run uses a new PID-keyed name and clears it at import — but they are never collected automatically, so ~/.claude/proxy/claude-retry-proxy-test-state-*.json files may be deleted by hand at any time.

Known limitation (accepted by user decision, 2026-10-03). The product side is deliberately unchanged: a proxy killed outside claude-retry-proxy stop (Task Manager, taskkill /F, crash, power loss) can leave ~/.claude/proxy/proxy-state.json holding a dead PID, and a later start can be refused with Proxy already running once Windows recycles that PID. Recovery is to delete the stale file. Hardening options (an advisory port probe, recording OS process creation time) were presented and declined.

The ordering matters and is load-bearing: settings.py binds these paths at import and both cli.py and server.py import it, so setting the variables after import has no effect. tests/_harness.py does the assignment at module scope, before importing anything that reads them.

Because PROXY_STATE_FILE is also what CLI subprocesses read, the harness and the spawned CLI agree on which state file is current — so a test that starts and stops a proxy is checking its own proxy, not yours.

Per-Test Descriptions

Every test in the suite, grouped by the area it exercises. Use it to find which test covers a behaviour before writing a new one — the suite's cost is in the proxy and mock-upstream processes each test starts, so a duplicate is expensive. Descriptions are the test's own docstring, shortened.

This inventory is maintained by hand, and nothing verifies it. It is reconciled in the same commit as the test it documents — the pattern the sibling project uses. There is no generator: a test added without an entry here is missing silently. To list what is actually in a module: 
python - <<'EOF'
import ast, pathlib
for p in sorted(pathlib.Path('tests').glob('test_*.py')):
    t = ast.parse(p.read_text(encoding='utf-8'))
    for n in t.body:
        if isinstance(n, ast.FunctionDef) and n.name.startswith('test_'):
            print(n.name, '-', (ast.get_docstring(n) or '').split('\n')[0])
EOF

Testing patterns

Assert on the wire, not on the return value

The proxy's contract is what it sends upstream and what it returns to the client. A test that only checks the returned body will not catch a wrong auth header, a missing path rewrite, or a stripped field. Point a mock upstream at the proxy, capture the request, and assert on it.

Use the trace log as the internal observation channel

Internal decisions — which mode dispatched, whether a retry happened, whether a tool call degraded — are not visible in the response body. They are recorded as trace events, and _trace_events_for_request(request_id) retrieves them by correlation id. This is the sanctioned way to assert on internals, and it avoids reaching into module state.

Let the harness own the paths

Never hard-code a trace, state, or keys path in a test — build a temp directory and let the fixture builders place the files. A test that writes to a real path will pass locally and fail whenever a proxy is running.

Anti-patterns

Don'tWhy
Hard-code a portCollides with a live proxy or a parallel run. Use find_free_port().
Assert on a trace file path you chose Bypasses the isolation the harness establishes, and will read the wrong file.
Test a transform by calling it directly and checking the return value only Misses the failure path — a transform that raises falls back to the original body, which a direct call cannot exercise.
Mock the upstream with a plain socket echo The mock upstreams exist to record requests and to script per-request responses. A raw echo loses the recording.
Rely on ordering between independent tests Tests share a session temp directory and a set of ports; do not assume a clean slate beyond what a fixture builds.

Adding a test

  1. Put it in the module matching the area it exercises (see the catalog).
  2. Add the function to that module's ALL_TESTS list — the aggregator picks it up from there.
  3. Build fixtures with the harness helpers rather than inline setup.
  4. Verify it runs both alone (-t <name>) and as part of the full suite, and that the full suite passes with a live proxy running.

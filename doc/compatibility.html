Compatibility LearnerHow the proxy learns, per provider-model pair, what an upstream will accept

Last updated: 2026-09-30

Third-party providers that speak the Anthropic wire format do not always implement every field, and they disagree about how to echo an assistant turn's reasoning. Neither fact can be known in advance, and neither failure is visible to you — the request simply fails. So the proxy learns both, per provider-model pair, and adapts.

The learner is a registry of features, each naming a policy the proxy runs for a request that carries the thing it cares about. Two are registered:

FeatureModeLearns
context_managementanthropic Which upstreams reject the field — strips it, and re-tests whether support has arrived
reasoning_fieldchat Which reasoning-echo field a chat upstream wants — reasoning_content, reasoning, or none at all

A feature's mode is the endpoint mode it runs in, so the two policies never see the same request. This page documents both: the first is a state machine that changes behaviour over time, the second a three-value selection learned from upstream complaints.

Scope. Each feature declares the endpoint mode it runs in and runs in no other: context_management is anthropic-mode only, reasoning_field is chat-mode only, and response mode runs neither. count_tokens requests are excluded, and so are compatibility retries themselves. See provider-modes.html.

Policy constants

These are maintainer-tunable and have no user-facing configuration surface. They live at the top of the compatibility learner module, src/claude_retry_proxy/compat.py.

ConstantValueMeaning
COMPAT_INITIAL_THRESHOLD32 Strips before the first revalidation probe
COMPAT_PROBATION_THRESHOLD8 Strips between probes while in the probation state
COMPAT_BACKOFF_MULTIPLIER2 Factor by which the threshold doubles after a repeated rejection
COMPAT_MAX_THRESHOLD4096 Ceiling on the threshold
COMPAT_DELISTING_SUCCESSES2 Consecutive probe successes required to delist
COMPAT_MAX_RETRIES_PER_REQUEST1 Compatibility retries per client request for context_management. The budget is per-feature: reasoning_field declares 2, because its walk may need to reach a third candidate
COMPAT_FAILED_CONFIRMATION_SUPPRESSION3 Failed confirmations before the key is suppressed
COMPAT_REASONING_SWITCH_THRESHOLD3 Consecutive complaints before reasoning_field moves to the next candidate

Startup validates the relationships between these rather than trusting them. Each violation prints a warning on stderr and clamps the value — it does not refuse to start: COMPAT_BACKOFF_MULTIPLIER is raised to at least 2, COMPAT_DELISTING_SUCCESSES to at least 2, COMPAT_INITIAL_THRESHOLD is lowered to COMPAT_MAX_THRESHOLD if it exceeds it, and COMPAT_REASONING_SWITCH_THRESHOLD is raised to at least 2 (a value of 0 or 1 would collapse the three-strike rule to a single strike).

That last clamp is worth a note, because it was the one clamped constant whose consumption crossed a module boundary. The threshold is compared inside the learner module — at the persist site, under the state lock — but an earlier arrangement imported the constant by value into server.py and compared it there. The clamp rebinding the learner's global then had no effect on the decision, so the warning printed and the un-clamped value was used anyway. The comparison now reads the learner's own binding, which is what makes the guard a guard.

The registry itself is COMPAT_FEATURES, a name → descriptor mapping; each descriptor carries its mode, its presence test, its complaint matcher, its learning policy, its entry field set, its retry budget and its own retry lock. COMPAT_FEATURE remains as the "context_management" name constant, and COMPAT_SCHEMA_VERSION is 1.

Scope and states

Learned state is keyed by the tuple (provider, mode, actual_model, feature). The model is part of the key, so two tiers pointing at the same provider but different models learn independently — which matters, because a provider may proxy several backends with different capabilities.

In memory the learned set is a single owned _CompatState object (_state in compat.py): its entries dict holds the keyed entries and its lock serializes access and persistence. The learner functions take the state by default parameter (state=_state), so tests can inject a fresh instance. Each feature owns its own retry lock — a descriptor property rather than a module-global — so one feature's slow retry can never deny another feature its retry. For context_management the forward path in server.py reaches that lock through the module-level aliases _compat_state_lock / _compat_retry_lock, which remain importable for the tests that assert the alias identity. The retry lock's acquire/release discipline belongs to its caller, which holds it across the unstripped probe's upstream HTTP call.

The context_management states

This feature has exactly two states. The vocabulary is per-descriptor, so it says nothing about the other feature's:

StateMeaning
unsupportedThe upstream rejected the feature; strip it pre-emptively
probationThe upstream accepted a probe; strip, but re-test sooner
"Delisted" is an event, not a state. When an entry is delisted it is removed from the state dictionary entirely — the proxy reverts to sending the field and learning from scratch if it is rejected again. There is no third "supported" state, and consequently no persisted record that a provider was ever known to be fine.

Transitions

↓

↓  32 strips

↓

Learning

An entry is created when a request carrying the feature is rejected with a recognised 400 and a single stripped retry then succeeds. The new entry starts in unsupported with threshold = COMPAT_INITIAL_THRESHOLD (32) and all counters at zero. Learning also clears the failed-confirmation counter for the key.

Stripping and the effective threshold

Each request carrying the feature for an already-known key increments a strip counter. The counter is compared against an effective threshold that depends on state:

StateEffective threshold
unsupportedthe entry's own threshold
probationCOMPAT_PROBATION_THRESHOLD — always 8

So a provider that has shown signs of supporting the feature is re-tested four times more often than one that has never accepted it.

Probing

A probe is a request sent without stripping. Only one probe may be in flight at a time across the whole proxy — the throttle is a single lock, not one per key — and it is acquired non-blockingly. If it is unavailable, which is the common case under concurrency, the request strips instead of probing and does not disturb the state machine. The strip counter resets to zero when a probe starts, so strips that occur concurrently with an in-flight probe count toward the next threshold rather than the current one.

The proxy-wide scope has a fairness consequence worth knowing: a slow probe for one provider holds the lock for the duration of its upstream call, so threshold-reaching for every other provider and model is delayed until it completes. Those requests strip rather than probe, so none of them loses state — they simply wait their turn to be re-tested.

The probe's response is interpreted in three ways:

Probe resultEffect
2xx Increments the success count and resets the strip counter. At COMPAT_DELISTING_SUCCESSES (2) the entry is removed; below that the entry moves to (or stays in) probation.
matching 400 Resets the success count, returns the entry to unsupported, resets the strip counter, and doubles the threshold — capped at 4096. The client still gets a working response: the proxy immediately retries once with the stripped body.
anything else Inconclusive. State and success count are left unchanged; only the strip counter is cleared. No evidence is inferred from an ambiguous result.

The doubling ladder is what stops a permanently-incompatible provider from being re-tested forever: 32 → 64 → 128 → … → 4096, after which probes become rare enough to be free in practice.

What counts as a "matching 400". The proxy recognises two specific shapes, and deliberately not a general one. One is a message-form match anchored so the feature token must appear at the start of the message or immediately after ": " or "] " — which means a dotted path such as tools.0.context_management never matches. The other is a structured validation error whose location ends at the feature at top level, and is not a nested path. A 400 that does not match is treated as a client error and is not learned from.

Upstream error text is only ever matched against these patterns — it is never copied into state keys, strip logic, or trace events.

Suppression

A key whose rejection keeps failing to be confirmed is eventually left alone. This branch has no configuration surface and is easy to miss when reasoning about why a provider stopped being probed.

  • Each time a stripped retry also fails to confirm the learned state, a failed-confirmation counter for that key increments.
  • At 3 (COMPAT_FAILED_CONFIRMATION_SUPPRESSION) the key is suppressed: the learner stops probing it.
  • A request that arrives while suppressed is counted and skipped, and a compatibility_failed_confirmation_suppressed event is recorded.
  • After 32 suppressed requests — the same value as COMPAT_INITIAL_THRESHOLD — the counter is cleared and the key re-enters discovery.

The effect is a slow retry: a provider that cannot be reasoned about is dropped from active probing, then quietly re-examined after enough traffic has passed. The 32-request reset is counted per key, so a rarely-used model re-enters discovery very slowly.

The reasoning_field feature

Chat upstreams disagree about how an assistant turn's reasoning is echoed back. OpenAI's chat-completions shape has no such field, so each vendor invented one: DeepSeek and GLM read reasoning_content, vLLM reads reasoning, and some accept neither. Until this feature existed the proxy hedged by writing both — which gateways that are strict about unknown pairs reject outright with a hard 400, and which always serialized the reasoning text twice.

The proxy no longer guesses. It sends one field, learns which one a pair wants from the upstream's own complaints, and defaults to sending nothing.

Three pieces of state, one rule

StateWhereMeaning
selectionpersisted reasoning_content or reasoning. An absent entry means none — the default is never written, because it requires no entry
complaintsin memory The pair (for_selection, count) — consecutive matched complaints counted against that one selection
latchedin memory Set once the full-walk outcome has been seen on two consecutive requests

The rule in one paragraph: send the selection; on a complaint, count it and try the next candidate inside the same request so the client is still served; persist a switch only once the count reaches three; and if all three candidates complain within one request — a full walk — on two consecutive requests, latch the pair to none until the process restarts.

Four details are load-bearing:

  • The counter belongs to a selection. It is the pair (for_selection, count), compared against the selection the request actually sent — never against the entry's current value. That is what makes a persisted switch reset the count implicitly (the next complaint carries a different selection, so it is the first complaint against the new one), and what keeps a complaint attached to the selection it was aimed at when a switch lands concurrently.
  • The reset is the request's own outcome. A request whose forwarding pass ends 2xx sets the count to zero — an upstream 429/503 that the retry loop carried to a 2xx counts, because it was served. A walk candidate's own success neither resets nor increments the strike count.
  • A request with no thinking block is inert. It neither exercises the selection nor proves anything about it, so it mutates nothing. Letting such a request reset the ladder would make the threshold unreachable for any pair that interleaves ordinary chat with thinking-bearing turns.
  • Absent means none. The default needs no entry, so there is nothing to settle on a plain success — and the same one rule protects a settled reasoning_content, a settled reasoning, and the default alike.

The in-request walk

A complaint is answered inside the same client request: the proxy advances to the next candidate in the cycle none → reasoning_content → reasoning → none and re-sends it, up to the feature's budget of 2 extra attempts. The client is therefore served transparently while a pair is learning, and the third candidate is reachable within one request. Each step re-enters the forward path with the original client body and suppress_compat set, so the chat transform re-runs with the new candidate.

Walk step resultEffect
2xx The client is served. A switch is persisted only if the count has reached the threshold, and the persisted candidate is the one that just succeeded — or, when that candidate is none, the entry is removed (absent means none).
matching complaintAdvance to the next candidate.
anything else Stop the walk, change nothing, and return the client its original error rather than the walk's. A 401, a 500, a connection error or a 429/503 is no evidence about the field, so nothing is counted and nothing latches.

Only one walk runs at a time per feature, under the feature's own retry lock, acquired non-blockingly. When it is contended the request issues no retry, mutates no counter, and the upstream error reaches the client unchanged. Because the lock is per-feature rather than module-global, a chat-mode walk can never deny an anthropic-mode probe its retry. The cost is real but bounded: a walk is up to three upstream attempts, so a stuck chat upstream can hold one worker thread — and delay a concurrent admin switch's drain — for several minutes.

What counts as a complaint

Status 400, plus one of two content shapes, both built from the proxy's own field-name constants and nothing else:

  • Message form — a message value in the parsed body names a field. The traversal reads parsed message values only: never bare keys, never the raw body. A gateway that echoes the offending request back as nested JSON therefore cannot hand the matcher its own request text.
  • Structured form — a validation node carrying extra_forbidden whose loc/location list ends with a field name. This is how a gateway reports a rejected field when no message string names it; without it, such a pair would never register a complaint at all.

There is deliberately no phrase matching: the prose is upstream-authored and will drift, while an upstream complaining about the reasoning field must name it. The trigger is therefore keyword-grade rather than field-reference-grade — the bare English noun reasoning matches unrelated prose such as "max_tokens must be greater than the reasoning budget". That is the accepted cost of a deliberate bias toward recall: a missed complaint means the pair never learns, which is the pre-existing behaviour, while a false positive costs one increment and needs two more consecutive ones before anything moves. A field name buried in a message string that merely echoes the request would also match; that hole is recorded rather than closed, because closing it would mean matching on prose again.

A 400 that names no field is not a complaint. A 401/403 (account disabled), a 500 (gateway blip), an unparseable body, or a 400 naming no field in either shape is not counted: nothing advances, nothing latches, and the error passes through untouched. The same is true of any status other than 400 — a gateway reporting the condition as a 422 produces no complaint, so such a pair silently stays at none. That is a known limitation of the design, not an oversight.

Latching

A full walk — all three candidates complaining within one request — is one observation, not three: the same upstream condition, examined three times with only the field differing. A uniform 400 unrelated to the field repeats identically across all three, so one such request must not latch a pair for the process lifetime. The latch is earned the way a switch is, by repetition: the full walk must recur on two consecutive requests, where consecutive means any intervening feature-active success clears the evidence — a walk candidate's own 2xx included, since a working candidate is exactly the evidence that "no candidate works" is false.

A latched pair sends none, issues no retries, mutates no counters, and leaves the persisted selection untouched: the latch is a decision about this process, not a rewrite of what was learned, so the next run starts from the last known-good state. It emits a compatibility_latched trace event and a stderr warning, both metadata-only, and a restart is its only reset.

Persistence

Learned state is written to ~/.claude/proxy/feature-compatibility.json (overridable with PROXY_FEATURE_COMPAT_FILE). Writes are atomic: a temporary file is written and then renamed into place, so a crash mid-write cannot leave a truncated state file.

FieldMeaning
schema_versionCurrently 1
provider, mode, actual_model, feature The shared envelope and the key, serialised with a \x1f (unit separator) delimiter so a value containing an ordinary separator cannot forge a collision. The in-memory key is derived from the entry's own envelope, so a file whose key disagrees with its body cannot be loaded under the wrong one
state, threshold, strip_counter, probation_successes context_management only. Its state vocabulary (unsupported or probation), the current strip threshold, and its progress counters
selection reasoning_field only. The learned echo field — reasoning_content or reasoning. An absent entry means none: the default is never written

The field set is per-descriptor. Each descriptor validates its own values on load, so a value outside its vocabulary — an unknown selection, say — rejects the entry rather than loading it, and a descriptor returns nothing for anything it cannot validate instead of raising.

On load, the threshold is snapped onto the doubling ladder rather than trusted, so a hand-edited or corrupted value cannot produce an off-ladder threshold. Entries that fail validation are dropped individually with a redacted warning — one bad entry does not discard the file.

Counters reset to zero on load, by design. A restart forgets how many strips a provider has accumulated and how many probe successes it had. The direction of the resulting error is deliberate: the proxy will over-strip (harmless — the upstream simply never sees a field it did not want) rather than under-strip (which would surface as repeated client-visible failures). A restart therefore cannot delist a provider; it can only delay one.

If the state file is unreadable or malformed, the proxy fails open with empty state and a warning. It does not refuse to start.

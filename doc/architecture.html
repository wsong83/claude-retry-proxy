ArchitectureHow a request is routed, retried, and rewritten

Last updated: 2026-09-12

This page describes the path a request takes from the moment it reaches the proxy to the moment a response leaves it. It is the reference the other pages link back into — in particular Retry and backoff and Trace and state sinks, which between them explain most of the proxy's surprising behaviour.

Overview

The proxy is a ThreadingHTTPServer bound to 127.0.0.1 (default port 8080, overridable with PROXY_PORT). It is a gateway, not a transparent forward proxy: it parses enough of each request to decide where the request should go and what it should look like when it gets there.

Two ideas carry most of the design weight:

  • Tier routing. The client asks for a model by name. The proxy maps that name to one of three tiers (haiku, sonnet, opus), and each tier is independently pointed at a provider and a model. Switching a tier's provider is a config change, not a client change.
  • Upstream variability is absorbed, not exposed. Providers differ in which features they accept, which endpoint shape they speak, and how often they return 429. The proxy retries, rewrites, and — for one specific Anthropic feature — learns per upstream. See compatibility.html.

The request path

Each request is handled independently on its own thread. The sequence below runs in ProxyHandler.do_POST and forward_request in src/claude_retry_proxy/server.py.

Step 1 — Extract the model

extract_model(body_bytes) parses the request body and reads its model field. It returns the literal string "unknown" when the body is empty, is not valid JSON, or has a missing, null, or non-string model.

Step 2 — Resolve the tier

resolve_tier(model_name, config) maps that name onto a tier. See Tier resolution below. An unresolvable name is a client error, not a fallback.

Step 3 — Look up the provider and model

The tier names a provider and the concrete model name to send upstream. The provider's entry in the decrypted keys file supplies the base URL, the credential, and the mode.

Step 4 — Dispatch on mode

The mode (anthropic, chat, or response) determines the auth header, the upstream path, and how the request and response bodies are transformed. This is a large enough subject to have its own page — see provider-modes.html.

Step 5 — Forward and retry

A fresh connection is opened to the upstream per attempt, with a 300-second socket timeout, and the retry loop in Retry and backoff takes over.

Step 6 — Rewrite the response model

On success, the model name in the response is replaced with the tier name the client originally asked for, so the client sees the name it sent rather than the provider's internal model id. The mechanism differs by content type and mode; see provider-modes.html.

Step 7 — Trace

One JSONL record is appended describing the outcome. See trace-log.html.

Request bodies are transformed once per forward. The outbound body is built before the retry loop starts and is never rebuilt on a retry. A retry re-sends bytes, it does not re-transform them. The one exception is the compatibility retry: it strips the feature from the client body and re-enters the forward path, so that path runs the transform again — one upstream attempt, but a fresh pass. See compatibility.html and provider-modes.html.

Tier resolution

resolve_tier applies four rules in order and stops at the first that matches. The order matters: an earlier rule always beats a later one.

#RuleExampleResult
1 Guard on type. A None or non-string model name cannot be resolved. null unknown
2 Direct match — the name is already a tier name. sonnet sonnet
3 Reverse lookup — scan the configured tiers for one whose model equals this name. a name a tier is currently pointed at that tier
4 Pattern match — case-insensitive substring search, tried in the order opus, sonnet, haiku (most specific first). claude-opus-4-5 opus

A name matching none of these resolves to unknown, and the proxy returns an error rather than guessing a tier.

Two tiers may share a model name. Response rewriting uses the tier resolved for this request, not a reverse map from model name to tier — so a shared name never makes the rewrite ambiguous.

Retry and backoff

The retry loop lives in _forward_core. It retries exactly three conditions: HTTP 429, HTTP 503, and connection-level errors (socket.error, ConnectionError, OSError). Every other status is returned to the client immediately rather than retried. Whether its body is rewritten on the way out is mode-dependent — see provider-modes.html.

How many attempts

The loop runs PROXY_MAX_RETRIES + 1 times — the +1 is the initial attempt, so the default PROXY_MAX_RETRIES=10 means 11 attempts, i.e. 10 retries.

Exception — count_tokens. When disable_retry_claude_count_token is set in config.json and the request targets count_tokens, the loop runs exactly once. Most third-party providers do not implement this Anthropic-specific endpoint and answer it with 503; retrying ten times would burn quota for nothing. The shipped template enables this.

The delay ladder

The exponential base is PROXY_INITIAL_DELAY × 2^attempt, capped at PROXY_MAX_DELAY. With the shipped defaults (initial 1 s, cap 30 s) the ladder is:

11 s

48 s
516 s
6+30 scapped — the ladder stops growing here

The cap is applied before jitter, so an actual sleep can exceed PROXY_MAX_DELAY by up to 25%.

The cap is applied before the exponential on the 429 path — and is not applied afterwards. A 429 does not use the ladder at all: it sleeps PROXY_MAX_DELAY directly (default 30 s, jittered). A 503 and a connection error both use the ladder above. So a 429-heavy request sleeps far longer than a 503-heavy one, and the distinction is deliberate: a rate limit means "come back later", not "back off gradually".

Jitter

Every delay is jittered by a uniform ±25% of its base. The implementation is worth knowing about because it is not the obvious one:

jitter = uniform(-0.25, 0.25) * base
return max(0, floor(base + jitter + 0.5))

It uses floor(x + 0.5) rather than Python's round(). That is deliberate: Python 3's round() is banker's rounding, which rounds halves to the nearest even integer and would collapse small even base values onto a single constant — removing exactly the de-synchronisation the jitter exists to provide.

Jitter is still degenerate at the small end for a different reason: because the result is rounded to a whole second, a base of 1 s or 2 s has a ±0.25 s / ±0.5 s range that lands entirely inside one integer bucket, so every client sleeps for exactly the same duration. Effective de-synchronisation starts at a base of 3 s. On the 503 path that is the third retry onward; on the 429 path the base is the full 30 s, so it de-synchronises immediately.

Worst case

With the shipped defaults a single stuck request holds a worker thread for:

ScenarioWorst-case hold
10 retries, all 503≈ 3.8 min
10 retries, all 429≈ 6.3 min
100 retries, 300 s cap (both env vars at maximum)≈ 10.4 hours

The last row is not hypothetical arithmetic — it is what the environment-variable bounds permit. Raising PROXY_MAX_RETRIES and PROXY_MAX_DELAY together is what produces it.

Give-up behaviour

When the retry budget is exhausted the two families of failure behave differently, and the difference is visible to the client.

Condition exhaustedWhat the client receives
429 / 503 The upstream's original error body, drained and forwarded unchanged (capped at PROXY_MAX_BODY_SIZE). The client can read the provider's own explanation of why it was refused.
Connection error A synthesised JSON body of type upstream_unreachable, reporting the sanitised error and the retry count, returned with status 0. There is no upstream body to preserve.

Preserving the upstream body matters because a rate-limit response usually explains the quota situation, and discarding it would leave the client with a bare status code. The consequence is that those bodies also flow into the trace log when --all is enabled — see trace-log.html.

Response size caps

Two independent caps bound how much the proxy will move, and they sit at different layers:

CapApplies toOn breach
PROXY_MAX_BODY_SIZE The client's request body, and the upstream error body drained on the give-up path The request is refused with 413; the give-up drain is simply cut short
PROXY_MAX_RESPONSE_SIZE Every response body the proxy reads or forwards The response is truncated and a response_size_cap_exceeded trace event is recorded

The response cap is enforced at seven read loops: four for streamed responses — the silent forwarding path, the client-disconnect-aware path, and the two audit paths — and three in _forward_core for buffered reads (a 2xx application/json body, a 2xx body of another content type under a non-anthropic mode, and any non-2xx body). Every one of those sites emits the same event when it truncates, so a truncated response is visible in the trace rather than silently short.

Truncation is not something the client can act on beyond the missing bytes: on a streamed response the status and headers have already been sent by the time the cap is reached. The cap's real job is to stop an upstream that never ends from pinning a worker thread and growing the proxy's memory without bound.

Client disconnects

A client that closes the connection mid-response is a normal event, not a fault. The proxy catches it and records a client_disconnect trace event rather than failing the request, and the streaming path carries an inner handler for upstream read errors as well.

The catch is deliberately narrow — only ConnectionResetError, BrokenPipeError, and ConnectionAbortedError count as a disconnect. That is the set Python raises for an ordinary client-side close.

An accepted residual: a non-standard write error can be mistaken for a connection error. A client-write OSError outside that tuple — WSAENOBUFS, WSAENOTSOCK, ENOTCONN and their relatives — is not caught. Raised after response headers have been sent, it propagates into the retry loop's own except (socket.error, ConnectionError, OSError) clause and is read as a failed upstream connection, so the proxy re-issues a POST that had already been sent.

The class is exotic and Windows-only, and the consequence is bounded to a duplicate upstream call. It is documented rather than fixed because widening the catch would risk swallowing real upstream connection errors, which the retry loop depends on. The sharpest case is a streamed compatibility probe: the probe owner holds the single proxy-wide probe lock, so a re-issued POST is a duplicate unstripped probe whose outcome can spuriously double the threshold or reset probation. The next probe cycle revalidates, so the error stays bounded to one spurious doubling. See compatibility.html for the probe mechanics.

Configuration snapshots and drain-and-swap

Tier mappings can be changed while the proxy is running, which raises the obvious question: what happens to a request that is halfway through when the configuration changes underneath it?

The answer is that it never sees the change. forward_request takes a snapshot of both the configuration and the decrypted vendors at entry, under the same lock, and threads those snapshots through the entire call chain. A request admitted before a swap completes uses the old configuration from beginning to end.

drain-and-swap
administrator requests a change
↓
set _config_swapping — new requests block on _swap_done
↓
wait for _inflight_count to reach 0   (up to 30 s)
↓
swap configuration under lock → clear flag → signal _swap_done
↓
blocked requests proceed with the new snapshot

A request that is in-flight keeps running to completion with its original snapshot; the administrator waits for it rather than cancelling it.

The drain can time out, and the swap is then aborted. The wait is bounded at 30 seconds. A request sitting in retry backoff can easily exceed that — the default worst case is about 3.8 minutes (see Worst case). When the timeout expires the proxy abandons the swap, clears the swapping flag, and returns an error to the administrator. The configuration is left unmodified and the in-flight request completes normally. Nothing is corrupted — but the administrator's change did not take effect, and retrying it while the same slow request is still running will fail the same way.

The heartbeat

A background thread writes the proxy's liveness to proxy-state.json every 30 seconds, including the PID, port, and start time that claude-retry-proxy stop, status, and reload read.

The authoritative copy of that state is in memory. The heartbeat updates a module-level dictionary and writes that to disk; it never reads the file back. The practical consequence is that deleting proxy-state.json is recoverable — the next heartbeat rewrites it, complete, within 30 seconds. An external writer racing the heartbeat would be overwritten rather than merged.

Trace and state sinks

Both the trace log and the state file are written by the same guarded sink implementation in src/claude_retry_proxy/sinks.py. Two of its properties are load-bearing and explain most of the proxy's fault behaviour.

Writes never raise

Every sink write is wrapped such that it returns True or False and never propagates an exception. This is not defensive padding — it prevents two specific misbehaviours:

  • An OSError escaping a trace write would be caught by the retry loop's own except (socket.error, ConnectionError, OSError) clause and misread as a connection error, causing the proxy to re-issue an upstream POST that had already been sent.
  • An OSError escaping inside the heartbeat thread would kill that thread permanently, silently stopping liveness reporting.

Failure reporting and recovery

A failing sink is noisy once, then quiet, then loud again on recovery:

SituationBehaviour
First failure of an episodeReported on stderr immediately
Further failures, same episodeAt most one report per 60 s, carrying a count of the failures suppressed in between
A write succeedsThe episode closes and one resumed line is emitted with the episode's total failed writes

Because success closes the episode, an intermittent fault — one that alternates between failing and succeeding — reports on every new episode rather than being muted after the first minute. That is the intended reading: a flapping sink is more interesting than a steadily broken one.

Entries written during an outage are lost, not buffered. There is no queue. The resumed after N failed write(s) line is the only record of how many were dropped. If you need to know what happened during a gap, that count is the whole story.

Self-healing, and what does not heal

Both sinks redo their work on every call — the trace sink re-creates the directory and appends, and the state sink re-creates the directory, writes a temporary file, and renames it into place. So the transient failure classes heal on their own, with no restart and no operator action:

  • a deleted log file or directory
  • a transient file lock
  • a disk that was full and is no longer

A permanently unwritable path does not heal and needs a human: an ACL that denies the process, or a path that has been replaced by a directory.

Startup is the exception to "never stop the proxy". If either sink's path is unwritable at startup, the proxy exits non-zero before printing its readiness marker, and the CLI reports the failure. At runtime a broken sink degrades the proxy; at startup it refuses to run. The asymmetry is intentional — a proxy that cannot record what it did is not worth starting, but one that loses a few entries mid-flight is worth keeping.

Best-effort diagnostics

Shortly after the startup checks, the server replaces sys.stderr with a non-raising wrapper. Every later diagnostic write in the request path therefore cannot raise — which matters for the same reason the sinks are guarded: an exception from a print inside the retry loop would be caught by the connection-error handler and misread as a network failure.

The two startup ERROR prints deliberately run before the wrapper is installed, so they stay loud on a healthy stderr. The wrapper covers the request path only, not a module imported directly.

Shutdown

Shutdown is immediate rather than graceful, and that follows from one mechanism: worker threads are daemon threads, so the interpreter does not join them when the server closes. A request that is mid-retry or mid-backoff is killed, not awaited — the opposite of what drain-and-swap does with the same condition.

This is a deliberate trade, not an oversight: making shutdown wait would mean disarming the daemon flag and adding a bounded drain, which changes what stop does. What the client sees — and why the interrupted request's trace entry never lands — is owned by operations.html#shutdown.

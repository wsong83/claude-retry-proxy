OperationsRunning, inspecting, and stopping the proxy

Last updated: 2026-10-25

The claude-retry-proxy command manages a background server process. It does not run in the foreground. Understanding that split explains most of the command's behaviour: the CLI decrypts keys, validates configuration, and spawns a detached server; the server owns the listening socket and the request path.

The CLI

CommandWhat it does

stopReads the state file and terminates the process — gracefully first, then by force — and exits 1 without removing the state file if the process survives (see the stop contract)
statusReports running / stopped / stale, plus the current tier mapping
reloadRefreshes the provider catalog in the running proxy from models.json, without restarting it. It does not re-read the tier mapping — apply tier changes through the admin page. Refuses, naming the tier, if the reloaded catalog has dropped a model a tier is currently using

Two-phase readiness

After spawning the server, start confirms it is actually serving before reporting success. Two independent checks run in sequence, because they catch different failures.

Phase 1 — the READY marker

The CLI waits for the server to print READY on stdout, with a 5-second timeout. It is read by a daemon thread consuming stdout line by line.

This catches early failures — a wrong passphrase, a config validation error — before the socket is ever bound. Without this phase those failures would be indistinguishable from a slow start.

Phase 2 — the TCP probe

The CLI connects to the listen port, with a 2-second timeout. This confirms the server is genuinely accepting connections.

The marker is printed after the socket is constructed but before the server begins serving, so phase 1 alone would not prove the port is reachable.

If either phase fails, the CLI rolls back and reports what it saw — including the tail of the server's stderr, which is usually where the real error is. That tail is scoped to the current attempt: the log is append-only across runs, so a whole-file tail would print earlier sessions' lines as this start's cause.

A port held by another listener is refused by the child before READY, because its pre-bind probe and its listening socket use the same bind semantics. On POSIX both use SO_REUSEADDR, which tolerates a port left in TIME_WAIT while still refusing a second LISTEN. On Windows both use a plain bind, because Windows' SO_REUSEADDR would otherwise permit binding a port that already has a live listener — the duplicate bind is accepted and the readiness probe cannot tell whose socket answered. A plain bind on Windows still tolerates TIME_WAIT.

The line-by-line stdout reader replaced an earlier select.select() based approach that does not work with pipe file descriptors on Windows. On Windows, the current approach is the only one of the two that functions.

Passphrase protocol

The CLI decrypts the keys file itself to validate the configuration, then needs the server — a separate process — to decrypt it again for its own use. The passphrase is transferred over the child's stdin.

CLI prompts for the passphrase (input hidden)
↓
CLI writes <passphrase>\n to the server's stdin, then closes it
↓
server reads exactly one line from stdin in main(), before serving
↓
decryption failure → error on stderr, non-zero exit
↓
CLI observes the non-zero exit and reports a startup failure

When the keys file is plain JSON, no passphrase exists to send: the CLI closes stdin immediately and the server skips the stdin read entirely. The two processes therefore agree on the protocol by inspecting the same file, not by a flag.

--passphrase-file puts the passphrase in the process command line, where same-host process listings can read it. It exists for non-interactive starts — CI, supervisors, container entrypoints — where an interactive prompt is impossible. Prefer the stdin path (the default) whenever a human is present to type it.

Admin page and API

The admin page is served at http://localhost:<port>/admin/ and has two buttons, which do deliberately different things:

ButtonDoes
Apply Config Applies the tier mapping shown in the page: which provider and model a tier points at, and which credential it uses — without restarting the proxy. Writes config.json, as {"tiers": …} and nothing else, so a key left over from an older layout is dropped here.
Reload Providers Re-reads models.json and refreshes the catalog the page offers. It does not re-read the tier mapping, and writes no file at all. Refuses with 400 — naming the tier, provider, and model — when the reloaded catalog has dropped a model a tier is currently using; the previous catalog stays in effect.
MethodPathPurpose
GET/admin/ The admin page itself
GET/admin/api/config Current tiers (including each tier's key selection) and the model catalog
GET/admin/api/providers Available provider names
GET/admin/api/providers-detail Per provider: its mode and its key names
GET/admin/api/swap-status Whether a config swap is in progress: swapping, the in-flight count, how long the drain has been waiting, how long since the last upstream byte, and the configured silence budget (budget_s)
POST/admin/api/switch Update tier mappings
POST/admin/api/reload Reload the provider catalog from models.json. Never re-reads the tier mapping and writes nothing. 400 — naming the tier, provider, and model — when a tier currently in use is missing from the reloaded catalog; the previous catalog stays in effect
POST/admin/shutdown Stop the proxy gracefully

providers-detail returns key names only — never credential payloads. The admin page uses those names to populate its Key column. For a single-key provider the column shows a fixed, disabled default.

A switch validates the same rules a startup does: all three tiers must be present, provider names must exist, and each tier's optional key selector must name a real key of its provider. An absent selector is defaulted to the provider's first key and written back into the persisted configuration, so what is on disk always matches what is running.

A switch preserves everything it does not change: the models catalog, disable_retry_claude_count_token, and any extra_request_headers rules all survive a hot tier switch. Applying a switch cannot silently discard your header rules — but note the asymmetry: those three live in models.json, which the proxy never writes, so they survive in memory across a switch while the document written to disk holds only the tier mapping. See architecture.html#split-write.

What a switch or reload waits for

A switch and a reload share the same drain-and-swap: new requests are paused at admission, then the handler waits for the requests already in flight. That wait has no wall-clock cap — a healthy generation of any length is allowed to finish — but it does not wait out silence. When no upstream byte has arrived from any in-flight request for PROXY_SWAP_SILENCE_TIMEOUT (default 30 s), whatever is still running is treated as silent and evicted retryably rather than awaited. Retry chains never hold the drain: a request sleeping between attempts abandons at the press and returns 503 config_swap_restart, so its client retry lands on the new mapping. The full mechanism — and the accepted consequence that a swap can block new admissions for as long as its drain runs — is in architecture.html#config-swap.

Swaps are single-flight. A second press while one is in progress — a double-clicked Apply, or the CLI racing the page — is refused with 409 and the config_swap_in_progress code (see the error taxonomy; both the admin page and claude-retry-proxy reload unwrap the envelope's error object). No second drain is entered and the refused press changes nothing to the config. The page does not dead-end on that refusal: it attaches to the in-flight swap, keeps reporting it, and stays locked until the swap ends. The enforcement is server-side in _drain_for_swap(); the page's lockout is an affordance on top of it. A reload carries a second 409 of its own: it gates its candidate catalog before pressing, so if a switch completes its whole cycle between that gate and the install, the reload answers 409 config_reload_stale instead of installing tiers that predate the switch. Because the server emits that code because a concurrent switch completed, the page's tier row is one swap behind by construction: the page re-reads the row and unlocks only on a successful re-read; a failed re-read leaves the controls locked and says so. The same gate covers the third site — a page that loads with no swap running: the drain may have finished between that page's two reads, so its one-shot check re-reads the row as well, and a failed re-read keeps the controls locked and paints the sticky "reload this page before applying" line. In every case a possibly pre-swap row is what must not be left pressable, because /admin/api/switch carries no staleness guard of its own — only the reload path has one.

The page's swap-time behaviour. A press paints a sticky pending line that repaints at 1 Hz from /admin/api/swap-status; whenever a swap is in play — this page's press, one detected on load, or one it was refused into — both buttons and all nine tier selects are locked, so nothing can be edited against a mapping about to change. Locking the selects is what makes the completion re-render safe. The line reads "no need to refresh", not "do not refresh": a mid-swap refresh is harmless, because the fresh page's one-shot check detects the running swap, re-locks, and resumes the progress line. On completion the page re-reads the tier row before unlocking, because _current_config is still the pre-swap document during the drain and the page may have painted the mapping the drain was about to replace. If the status poll fails 5 times consecutively the line says the proxy is unreachable and that reloading is now safe — the controls stay locked, since an unreadable status is not evidence that no swap is running.

A successful press returns the drain's own detail: drained, waited_s, and inflight_at_swap. drained means "nothing was evicted" — not "the in-flight count reached zero" — and inflight_at_swap is the count at the moment of the press, so both are facts about the press rather than a race with it. GET /admin/api/swap-status reports the same information live while a press is pending, which is what the admin page's status line polls at 1 Hz. The CLI's reload waits up to 300 s for the drain; because the drain is unbounded server-side, a client-side timeout does not abort the swap — the message says so and points at claude-retry-proxy status.

Restarting the proxy after an upgrade. The server serves admin.html from a process-lifetime in-memory cache, so an upgraded page is not picked up until the proxy is stopped and started.

CSRF protection

Admin POST endpoints are guarded by an Origin check. The server rejects the request unless the header matches the proxy's own origin exactly:

Origin headerResult
http://localhost:<port>accepted
http://127.0.0.1:<port>accepted
http://[::1]:<port>accepted
nullrejected
absentrejected
any other originrejected

The match is exact, including the port — a browser page served from a different port cannot drive the admin API.

Non-browser clients must send an Origin header. curl does not add one by default, so pass it explicitly — -H "Origin: http://localhost:<port>". A missing header is rejected, not treated as trusted. The CLI's own stop and reload commands do supply it, so only hand-rolled requests need this. Admin request bodies are capped at 64 KB, and a body nested past the proxy's 500-level JSON nesting limit is refused with 400 (see architecture.html#nesting-limit). Both refusals keep the admin surface's flat body shape — {"error": …}, carrying "code": "nesting_limit_exceeded" on the nesting one — rather than the Anthropic error envelope the client-facing API uses.

Shutdown

Both claude-retry-proxy stop and POST /admin/shutdown terminate the process promptly — typically within about a second — regardless of what is in flight.

Shutdown kills in-flight requests; it does not drain them. A request that is midway through a retry backoff is terminated where it stands — the daemon-thread mechanism behind that is in architecture.html#shutdown.

The client sees a dropped connection, and that request's trace entry never lands — so a trace log can be missing the very request that was interrupted. The proxy_stop marker still appears, which is what tells you the proxy went down at that point.

This differs from the drain-and-swap used by config changes. The two paths treat the same condition — a request sitting in retry backoff — in opposite ways: a config swap abandons the chain at the press (returning it a retryable 503 so the client's own retry lands on the new mapping), while a shutdown kills it where it stands. For live work the difference is subtler: a swap waits for a generation to finish, and a shutdown does not wait at all.

The stop contract

Shutdown is asked for, not assumed — and the exit code reports what actually happened rather than what was attempted. claude-retry-proxy stop sends the graceful /admin/shutdown request, then waits up to 5 seconds, then force-kills if the process is still alive (taskkill on Windows, SIGTERM on POSIX). Every one of those bounds runs on a monotonic clock, so a wall-clock step cannot lengthen or shorten a documented deadline.

If the process is still alive after the force-kill, stop exits 1 and leaves proxy-state.json in place: that file is the one record which makes an orphan findable by a later stop, status, or reload. It is removed only once the process is confirmed gone, and never before the final liveness check. So Proxy: stopped and a removed state file mean the same thing — the proxy is not running — and a stop that could not finish says so instead of reporting success.

stop does not escalate to SIGKILL. PID liveness is not proxy identity: a state file whose PID has been recycled answers is_pid_alive perfectly well, and on POSIX an unreaped zombie answers it too. An unblockable signal aimed on that evidence would be destructive against an unrelated process — and because the state file is deliberately preserved on failure, every later stop would repeat the mistake. The SIGTERM above is therefore sent on best-effort liveness alone: a process that ignores it is unharmed, which is exactly the difference between SIGTERM and SIGKILL here.

Several of these paths can be relocated with environment variables (PROXY_TRACE_FILE, PROXY_STATE_FILE, PROXY_FEATURE_COMPAT_FILE, PROXY_KEYS_PATH), which is how the test suite keeps its proxies isolated from a live one. See configuration.html.

The state file

proxy-state.json is how the CLI finds a running proxy — stop, status, and reload all read it. If the CLI reports a proxy as stale, it has found a state file whose PID is no longer alive, which usually means the process died without cleaning up.

The file is a projection rather than the source of truth: the authoritative copy lives in the server's memory and is rewritten every 30 seconds, so deleting the file is harmless and an external edit is overwritten rather than merged. The mechanism is owned by architecture.html#heartbeat.

Configurationconfig.json, keys-index.json, and the environment

Last updated: 2026-09-12

Two files configure the proxy, and the split between them is the important thing to understand: config.json is safe to read, share, and commit; keys-index.json is not.

FileHoldsDefault location
config.json Which tier goes to which provider and model; which credential to select; the model catalog; retry and header policy ~/.claude/proxy/config.json
keys-index.json Provider base URLs and credentials ~/.claude/keys-index.json
Credentials live in keys-index.json, never in config.json. A config.json records which named key to use, not the key itself — so it is safe to version-control and to paste into a bug report. Keep that property: if you ever find a credential in config.json, something has gone wrong.

config.json

{
  "tiers": {
    "haiku":  { "provider": "example-provider", "model": "claude-haiku-4-5", "key": "" },
    "sonnet": { "provider": "example-provider", "model": "claude-sonnet-5",  "key": "" },
    "opus":   { "provider": "example-provider", "model": "claude-opus-5",   "key": "" }
  },
  "models": {
    "example-provider": ["claude-haiku-4-5", "claude-sonnet-5", "claude-opus-5"]
  },
  "disable_retry_claude_count_token": true,
  "extra_request_headers": {}
}

The tiers object

All three of haiku, sonnet, and opus must be present. Each names a provider and the concrete model to send upstream, and may name a key.

FieldRequiredMeaning
provideryes Must match a provider name in keys-index.json
modelyes The upstream model id sent in place of the client's tier name
keyoptional Names which credential to use from a multi-key provider. Empty or absent selects the first key. See Multi-key selection.

Extra tiers beyond the required three are permitted, and are reachable through reverse lookup — a client asking for a model name that an extra tier is pointed at resolves to that tier.

The models object

Maps each provider to the list of model names it offers. The admin page uses this to populate its model dropdown, which is why every tier's provider needs at least one entry here.

Each entry must be a non-empty list of non-empty strings. Note the validation direction: the proxy checks that every provider mentioned in config.json exists in keys-index.json. Providers in keys-index.json that no tier or catalog entry references are silently ignored, so you can keep credentials for providers you are not currently routing to.

disable_retry_claude_count_token

Boolean, optional, and one of the few settings with a real cost attached.

Setting it to true makes the proxy attempt the count_tokens endpoint once instead of retrying it up to PROXY_MAX_RETRIES times. The reason is that count_tokens is an Anthropic-specific endpoint that most third-party providers do not implement, and they answer it with 503 — which is exactly the status the proxy retries. Leaving the flag off therefore means every token count burns the full retry budget against a provider that will never succeed.

The shipped template sets it to true. Turn it off only if your providers actually implement the endpoint.

This flag is preserved across admin hot-switches and re-read from disk on reload. So are the models catalog and every rule under extra_request_headers: those three are carried across a switch by name, so switching a tier cannot silently discard your header rules. See operations.html#admin. This flag also interacts with the compatibility learner, which excludes count_tokens from its probing — see compatibility.html.

extra_request_headers

Optional. Attaches outbound headers to every request for a given provider, deriving the value from the incoming request. This exists for providers that expect a session or trace header the Anthropic API does not define.

{
  "extra_request_headers": {
    "example-provider": [
      { "header": "x-opencode-session",
        "from": ["X-Claude-Code-Session-Id"],
        "fallback": "request_id" }
    ]
  }
}
FieldRequiredMeaning
headeryes The outbound header name to set. Must match ^[A-Za-z0-9][A-Za-z0-9-]*$ and must not be a reserved name.
fromoptional A list of incoming header names to read, in priority order. The first one present and non-empty wins. Matched case-insensitively; values are stripped.
fallbackoptional Used when no from header yields a value. Either a literal string (stripped before sending), or the special token "request_id", which substitutes a fresh UUID for the request.

Resolution is total: a rule that is malformed, or whose from headers are all absent, degrades to using the fallback or to attaching no header at all. It never fails a request. Validation at startup and reload is strict, however — the resolver tolerates what the validator would have rejected, so a live proxy never sees a bad rule.

Two constraints are worth stating plainly because they are security-relevant:

  • Reserved names are rejected. A rule may not set proxy-managed headers (auth, Host, Content-Length, Content-Type, the forwarded allowlist) or hop-by-hop framing headers (Connection, Transfer-Encoding, Expect, TE, Accept-Encoding, Cookie).
  • from may not name the client's auth headers. authorization and x-api-key are forbidden as sources — copying a client credential into an arbitrary outbound header is not permissible.

Header names are unique per provider, compared case-insensitively, so x-session and X-Session in the same provider's list is an error rather than a silent override. Fallback values must be free of control characters and representable in latin-1, since they are written verbatim into an HTTP header.

Resolved values are recorded in the trace log on every request for a provider with rules — not only under --all. If a rule forwards a per-conversation identifier, that identifier lands in the trace file. See trace-log.html.

keys-index.json

{
  "vendors": {
    "example-provider": {
      "url": "https://api.example.invalid",
      "key": "sk-ant-api03-YOUR-KEY-HERE"
    },
    "example-chat-provider": {
      "url": "https://api.example.invalid",
      "key": "sk-YOUR-OPENAI-KEY-HERE",
      "mode": "chat"
    },
    "example-multikey-provider": {
      "url": "https://api.example.invalid",
      "mode": "chat",
      "keys": {
        "ALPHA": "sk-YOUR-FIRST-KEY",
        "BETA":  "sk-YOUR-SECOND-KEY"
      }
    }
  }
}
FieldRequiredMeaning
urlyes The provider's base URL
keyone of A single credential as a plain string. Its key name is always "default".
keysone of A name → credential object. Insertion order is the key order, and the first key is the default.
modeoptional anthropic (default), chat, or response. See provider-modes.html.

A vendor must carry exactly one of key and keys. Carrying both, or neither, is a startup error naming the offending vendor.

An empty string "key": "" is accepted at load with a warning, but every request through that provider then fails with 500 invalid_provider_key. The asymmetry is deliberate: it lets you stage a keys file before populating it, while making the consequence unmissable. A keys object with no surviving entries degrades to "default" rather than falling through to the key field.

Multi-key selection

A provider may hold several credentials. Which one a request uses is decided per tier, not per provider — so two tiers pointing at the same provider can bill to different keys.

  1. A tier's key field names the credential to use.
  2. If key is absent, null, or the empty string, the first key in the provider's keys object is used.
  3. A name that matches no key of that provider is a validation error — at startup, at admin switch, and at reload alike. It is never silently ignored.

Selection is by exact name. The admin page shows a Key column sourced from the provider's key names only — credential payloads are never sent to the browser. A single-key provider shows a fixed, disabled default.

Encryption and file permissions

The keys file may be either plain JSON or encrypted. The proxy detects the format from the file's first bytes:

  • A file beginning VimCrypt~03! is decrypted with the passphrase.
  • Anything else is parsed as plain JSON, and no passphrase is prompted for.
Plain JSON leaves your API keys unencrypted on disk. It is convenient for testing and automation, but the file is readable by anything that can read your home directory.

If you use plain JSON:

  • On Windows, chmod is a near-no-op — it sets only the read-only bit and has no group/other permission model. Restrict the file's ACL manually with icacls.
  • On POSIX, chmod 0o600 is applied automatically.

The recommended production approach is to encrypt with vim -n -x, which uses blowfish2 and produces the VimCrypt~03! prefix.

When plain keys are loaded the server prints a warning on stderr so the condition is visible in the log. --passphrase-file is only consulted for encrypted files; with plain keys it is ignored.

Environment variables

These are read by the server process at import time. Several have CLI equivalents on claude-retry-proxy start; where both exist, the CLI flag wins.

PROXY_PORT80801024–65535 Listen port
PROXY_MAX_RETRIES101–100 Retry attempts, shared by 429 and 503
PROXY_INITIAL_DELAY11–60 First backoff delay, in seconds
PROXY_MAX_DELAY301–300 Backoff cap in seconds, applied before jitter
PROXY_MAX_BODY_SIZE104857601024–104857600 Request body cap (bytes) → 413. Also caps the give-up error-body drain.
PROXY_MAX_RESPONSE_SIZE1048576001024–1073741824 Streaming response cap (bytes); exceeding it truncates with a trace event
PROXY_LOG_ALL""— Set to 1 to record full request and response bodies. See the warning in trace-log.html.
PROXY_TRACE_FILE~/.claude/logs/proxy-trace.jsonl Trace log path
PROXY_KEYS_PATH~/.claude/keys-index.json Keys file path
PROXY_STATE_FILE~/.claude/proxy/proxy-state.json Heartbeat state file. Override for test isolation.
PROXY_FEATURE_COMPAT_FILE~/.claude/proxy/feature-compatibility.json Compatibility state file. Override for test isolation.
A value outside its range — or one that does not parse as an integer — is silently ignored, and the default above is used instead. Nothing is written to stderr or to the trace, so an out-of-range setting is indistinguishable from an unset one. The one warn-and-clamp mechanism in the codebase governs the compatibility learner's internal constants, not these variables; see compatibility.html.

PROXY_IDLE_TIMEOUT is not in this table because it does not exist: the server defines no idle-timeout feature, and setting it has no effect.

Validation rules

Validation is strict and runs at startup, so a bad configuration fails loudly rather than producing confusing request-time errors. The proxy refuses to start when:

Condition
config.json is missing — the template is copied into place and the instructions printed instead
Any of the three required tiers is absent
A tier is not an object, or has an empty provider or model
A tier references a provider with no entry in keys-index.json
A provider in config.models has an empty, malformed, or all-blank model list
A provider in config.models has no entry in keys-index.json
A tier's key is present but not a string, or names no key of its provider
disable_retry_claude_count_token is present but not a boolean
Any extra_request_headers rule fails its type, charset, reserved-name, or duplicate check
Any vendor carries both key and keys, or neither
An invalid vendor mode is not a startup refusal. Startup prints a warning on stderr and carries on. The failure surfaces per request instead, as 500 invalid_provider_mode. See provider-modes.html.

The direction of the config↔keys check is worth restating, because getting it backwards is a common mistake: config is authoritative. Every provider named in config.json must exist in the keys file. Providers that exist only in the keys file are ignored.

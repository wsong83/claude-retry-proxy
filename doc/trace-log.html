Trace LogWhat the proxy records, and what it deliberately does not

Last updated: 2026-10-26

The trace log is a JSONL file — one JSON object per line — at ~/.claude/logs/proxy-trace.jsonl by default, overridable with PROXY_TRACE_FILE or --log. Every request the proxy forwards appends one request entry, and the proxy's own lifecycle and internal events append their own entries alongside it. Requests rejected before forwarding write nothing when the rejection happens before the body is read — a malformed Content-Length — and admin API calls never write a request entry; the rejections decided after the body is read do write one: the oversized-body 413, the nesting-limit 400, and the pre-routing 400s for an unrecognised model, method or path, each with the shape noted under the entry schema above. Over-deep upstream payloads are not rejections at all — they are forwarded or skipped, with a nesting_limit_exceeded event.

It is append-only and line-oriented on purpose: a partially written final line costs you one entry, not the file.

The request entry

This is the entry you will actually read. Every field below is present on every request entry unless noted.

The "present on every entry" invariant above has two exceptions. The oversized-body rejection and the nesting-limit rejection write their entries before routing, so they carry no tier and no provider — and, for the same reason, no client_user_agent either: both are written before the request is routed, and a client's User-Agent cannot cause a 413 or a nesting rejection. Their error fields differ in kind: the 413's message is a literal, while the nesting 400's carries the offset and the locator path — client-derived key text — into the entry. Separately, on the pre-routing 400 paths — an unrecognised model, a disallowed method, a disallowed path — the entry carries provider: null, even though the table above types provider as a string. Both follow from where the entry is written: at the point the request failed, before any provider had been chosen. (The key and client_user_agent fields have their own omit-when-unresolvable conditions, stated in their table rows — those are field conditions, not entry shapes.)
key is a name, never a credential. It records which of a provider's keys was selected — "default" for a single-key provider, or the name from a keys object. This field is recorded regardless of --all, and applies to any tier present in the configuration, not only the three standard ones.

Lifecycle markers

Three entries bracket each run of the proxy. They are what tell you the process was restarted, and they survive things the request entries do not.

EventFieldsWritten
proxy_starttimestamp, port, pid At startup, before the server begins serving
proxy_readytimestamp, port, pid At startup, immediately after the signal handlers are registered and after the READY stdout marker — still before serve_forever()
proxy_stoptimestamp, pid, requests_total, requests_retried During shutdown, in a finally block

The stop marker carries the run's request and retry counts, so a run's totals are recoverable from the marker pair even if you do not want to aggregate the request entries.

proxy_start and proxy_ready differ in what they promise. proxy_start says the process exists; proxy_ready says it is fully initialised — socket bound, heartbeat thread running, signal handlers registered. That last part is what makes it useful: a SIGTERM delivered before handler registration takes the default action, killing the process without running serve_forever's finally (so no proxy_stop marker and no state-file cleanup). Anything that signals the proxy on startup should wait for proxy_ready rather than proxy_start. See architecture.html#sigterm.

A missing request entry does not mean the request did not happen. Shutdown does not drain in-flight requests — a request killed mid-retry never writes its entry. If you are reconciling a trace against a client-side log and the counts disagree at the tail of a run, that is the likely cause. See operations.html.

Separately, the marker timestamps include a millisecond component (.000Z) that the request entries do not. A strict timestamp parser looking for one exact format will fail on the other.

These are the events emitted outside the compatibility learner. The learner's eleven events are listed in compatibility.html; together the two lists are the complete set the proxy can write.

The stream phase carries tier and provider and no model: the stream helpers never receive the resolved model name. The client is told separately, as a retryable 503 config_swap_restart or an in-stream error frame. See architecture.html#config-swap

Several of these are metadata-only by design. transform_failure, chat_sse_tool_degradation, and the learner's events carry counts and identifiers but never body content, so a failed transform cannot leak model output into the log.

The chat-mode SSE events

Two of the events above partition the chat-mode SSE lifecycle. Every chat-mode stream that returned 200 and started ends with exactly one of chat_sse_drain or chat_sse_truncated, unless the request aborts with an exception — a client disconnect, or an upstream frame shape the parser cannot read. A stream that delivered a finish_reason emits chat_sse_drain when its drain ends; a stream that never delivered one emits chat_sse_truncated at EOF. Because the two are exhaustive, an absent pair is itself a finding: that stream did not complete. A config-swap eviction preserves this partition: an eviction before finish_reason emits chat_sse_truncated and never synthesises a terminal, while an eviction inside the drain window emits chat_sse_drain with drain_exit: "swap_abort". Both also write a swap_abort event.

chat_sse_drain carries drain_exit, the reason the drain ended — "done" ([DONE]), "eof", "byte_budget" (the 64 KB budget), "time_budget" (the 5 s budget), "read_error" (the connection died), "response_cap" (the response size cap was hit), or "swap_abort" (a config swap completed inside the drain window, so the turn is closed retryably instead of being given a terminal on the old routing). Alongside it: drain_bytes and drain_ms for the cost, finish_reason for what the provider claimed, and three flags — tool_calls_seen (a tool-call delta reached the transform), emitted_tool_use (a tool_use block actually reached the client), and tools_declared (the client declared tools at all).

The late-frame fields answer a different question: how long the drain actually had to wait. late_frames counts the drain reads that carried frames arriving after the finish signal — one per chunk, not per frame within a chunk — first_late_ms and last_late_ms bracket the offsets of the first and last such read, and late_tool_call_ms is the offset at which a tool call arrived late — the one number that says whether the 5 s budget is generous or binding, since it measures a tool call that would have been lost without the drain. All four are null or zero for a stream that ended at the finish frame; the wait costs latency only when a provider goes silent after finish_reason.

The join that makes this a measurement. tools_declared together with emitted_tool_use gives, per provider, the rate of tool-bearing turns that emitted no tool_use — neither field expresses it alone, since emitted_tool_use: 0 is unremarkable on a turn that never declared tools. Join the pair to the request entry by request_id for the provider name.

chat_sse_unfinished_turn is the same condition detected live: tools declared, no tool call seen on the wire and no tool_use emitted, finish_reason: "stop", and text ending in a colon. It carries request_id, tier, provider, key, finish_reason, tool_calls_seen, emitted_tool_use, tools_declared, text_tail_len, messages_bytes, and rule. It is evaluated after the drain has ended, so a tool call that merely arrived late is never counted as one that never came; the text tail it matches on is held in memory only — the event records its length, not its content. messages_bytes is the serialized size of the messages array the marker was built from, and null when no marker was stored — it puts a skipped marker on the wire rather than leaving it to be inferred from session transcripts. The tool_calls_seen test is what keeps a proxy-side degradation — a tool call seen on the wire but never started as a block — from being counted as a model omission.

It also acts. With the retry nudge enabled (PROXY_CHAT_RETRY_NUDGE non-empty — the default) a fire closes the turn with a retryable error instead of a terminal sequence and arms a single-use in-memory marker; the next request that recovers the conversation consumes the marker, has the nudge text injected into its upstream copy, and logs chat_retry_nudge. A recovery that stalls again is not errored a second time: it logs chat_retry_passthrough and is closed with the normal terminal synthesis. With the variable set empty the event is a pure measurement again — every fired turn passes through, while chat_sse_unfinished_turn keeps being written. Behaviour, the store's bounds, and the kill switch: provider-modes.html.

A rescue re-emits the chat path's per-request events. When reasoning_field answers a complaint with the rescue, each pass is a nested pass through the forward path, so mode_dispatch, one reasoning_rescue event and the chat transform's events above (cache_control_stripped, redacted_thinking_passthrough, reasoning_field_injected — when it filled anything, tool_args_parse_failure, content_block_dropped) fire once per pass — up to three images for a single client request. The multiplicity is bounded by the feature's rescue budget (two passes), and it occurs whenever the upstream complains, so a complaint regime multiplies these event counts — not self-limiting the way the old walk was, which is why the per-pass reasoning_rescue event exists: it is what makes a multiplied trace legible.

Note what this does not affect. request entries are emitted once per client request, in the request handler, and a rescue pass never reaches that code — so per-request accounting such as scripts/analyze_proxy_trace.py, which counts request entries, is unaffected; the entry's retries field likewise keeps its 429/503-only meaning, because a rescue is not a retry. It is the mode_dispatch, reasoning_rescue and transform event counts that multiply, not the request counts.

The --all flag

--all (or PROXY_LOG_ALL=1) adds request_body and response_body to the request entry. Bodies are stored as parsed JSON where possible and as a decoded string otherwise.

--all writes raw prompts and completions to a plaintext file. Whatever you or your users send through the proxy — source code, credentials pasted into a prompt, personal data — ends up readable on disk. Enable it for debugging, then turn it off.

Two mitigations are worth knowing:

  • Streamed 2xx response bodies are never captured, even under --all. A streaming success is consumed by the client in real time, so there is no buffered body to record. This is a deliberate reduction in data-at-rest exposure, not an oversight. Error-path bodies are captured.
  • The trace file is set to owner-only permissions on POSIX (chmod 0o600).

File permissions on Windows

On Windows, chmod is a near-no-op. It sets the read-only bit and nothing else — Windows has no POSIX group/other permission model for chmod to express. The trace log, the state file, and the keys file are therefore readable by any account that can reach your home directory unless you restrict them yourself.

Restrict the directory ACL manually with icacls. This applies to ~/.claude/logs/ and ~/.claude/proxy/, and it applies whether or not you use --all, because error text, resolved extra-header values and the client User-Agent are recorded regardless.

Two entry fields are not gated by --all: extra_request_headers and client_user_agent. The nesting_limit_exceeded event is not gated either: its path is client-derived key text and is written whether or not --all is on. Resolved header values — for example a client's per-conversation session identifier — are recorded on every request for a provider that has rules; if you configure such a rule, assume that identifier is in the trace log. The client_user_agent field is ungated for the same reason it exists: a User-Agent refused at the edge is refused on an ordinary request, so a diagnostic that required --all would be absent exactly when it is wanted. Its value is arbitrary raw client text with no allowlist — so treat it as untrusted, and note that it is not alone in that: method, path and model are also verbatim client strings, and extra_request_headers copies client header values too. The sink escapes every one of them (json.dumps with ensure_ascii), which keeps the file one entry per line and free of raw control characters — but escaping is not trust: each is still whatever the client sent.

Pruning

Each claude-retry-proxy start removes entries older than 5 days before launching the server. There is no separate rotation or size cap.

Pruning is best-effort and never blocks startup: a log locked by another process is left alone rather than failing the start. Entries are matched by their timestamp; a line the parser cannot read is left alone rather than discarded, so a malformed line persists until it ages out by whatever other means you apply.

Analysis

scripts/analyze_proxy_trace.py aggregates the log per model:

MetricMeaning
Request countEntries in the window
Average retriesRetries per request
Query success rateSuccess treating all retries of one request as a single query
Attempt success rateSuccess counted per upstream attempt
Geometric-mean TTFTTime to first byte, geometric mean
Geometric-mean latencyTotal latency, geometric mean

Two filters keep an outage from dominating the averages: requests with a latency above 30 minutes, and requests at maximum retries that also failed — the signature of a complete upstream outage rather than normal operation.

python scripts/analyze_proxy_trace.py --days 3
python scripts/analyze_proxy_trace.py --days 7 --trace-file /path/to/proxy-trace.jsonl

--days defaults to 3. The geometric mean is used rather than the arithmetic mean because latency distributions are heavily right-skewed: a handful of slow requests would otherwise move the average far away from anything a user experiences.

When writes fail

The trace file is written by a guarded sink that never raises. A failing sink reports the first failure of an episode on stderr immediately, then at most once per 60 seconds while the episode continues, and emits a resumed after N failed write(s) line when writing succeeds again.

Entries written during an outage are lost, not buffered. There is no queue and no replay. The count in the resumed line is the only record of how many entries were dropped — if you need to know what happened during a gap, that number is the whole story.

The failure mode is also the noisiest thing you can do to this log: an unwritable trace directory means every request loses its entry until the condition is fixed. See architecture.html for the full policy.

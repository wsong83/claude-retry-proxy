Trace LogWhat the proxy records, and what it deliberately does not

Last updated: 2026-09-12

The trace log is a JSONL file — one JSON object per line — at ~/.claude/logs/proxy-trace.jsonl by default, overridable with PROXY_TRACE_FILE or --log. Every request the proxy forwards appends one request entry, and the proxy's own lifecycle and internal events append their own entries alongside it. Requests rejected before forwarding — a malformed Content-Length, or any admin API call — write nothing.

It is append-only and line-oriented on purpose: a partially written final line costs you one entry, not the file.

The request entry

This is the entry you will actually read. Every field below is present on every request entry unless noted.

FieldTypeMeaning
timestampstringUTC, YYYY-MM-DDTHH:MM:SSZ
eventstringAlways "request" for this entry type
request_idstringCorrelates this entry with every other entry for the same request
methodstringHTTP method of the client request
pathstringRequest path (count_tokens is distinguishable here)
modelstringThe upstream model actually requested
tierstringThe resolved tier
providerstringThe provider that served it
keystringThe resolved key name. Omitted entirely when resolution is impossible.
statusstring"success" or "failure"
http_statusnumberUpstream status. 0 means a connection-level failure.
retriesnumberHow many retries were performed
total_latency_secnumberEntire request, including all retry waits. Rounded to 3 decimals.
first_byte_latency_msnumber or nullTime to first byte; null when not measured
errorstring or nullRedacted error text on failure; null on success
extra_request_headersobjectOnly present when non-empty — the resolved extra-header values for this request
request_body, response_bodyanyOnly under --all — see below
The "present on every entry" invariant above has two exceptions. The oversized-body rejection writes its entry before routing, so it carries no tier and no provider. Separately, on the pre-routing 400 paths — an unrecognised model, a disallowed method, a disallowed path — the entry carries provider: null, even though the table above types provider as a string. Both follow from where the entry is written: at the point the request failed, before any provider had been chosen.
key is a name, never a credential. It records which of a provider's keys was selected — "default" for a single-key provider, or the name from a keys object. This field is recorded regardless of --all, and applies to any tier present in the configuration, not only the three standard ones.

Lifecycle markers

Two entries bracket each run of the proxy. They are what tell you the process was restarted, and they survive things the request entries do not.

EventFieldsWritten
proxy_starttimestamp, port, pid At startup, before the server begins serving
proxy_stoptimestamp, pid, requests_total, requests_retried During shutdown, in a finally block

The stop marker carries the run's request and retry counts, so a run's totals are recoverable from the marker pair even if you do not want to aggregate the request entries.

A missing request entry does not mean the request did not happen. Shutdown does not drain in-flight requests — a request killed mid-retry never writes its entry. If you are reconciling a trace against a client-side log and the counts disagree at the tail of a run, that is the likely cause. See operations.html.

Separately, the marker timestamps include a millisecond component (.000Z) that the request entries do not. A strict timestamp parser looking for one exact format will fail on the other.

Several of these are metadata-only by design. transform_failure, chat_sse_tool_degradation, and the learner's events carry counts and identifiers but never body content, so a failed transform cannot leak model output into the log.

The --all flag

--all (or PROXY_LOG_ALL=1) adds request_body and response_body to the request entry. Bodies are stored as parsed JSON where possible and as a decoded string otherwise.

--all writes raw prompts and completions to a plaintext file. Whatever you or your users send through the proxy — source code, credentials pasted into a prompt, personal data — ends up readable on disk. Enable it for debugging, then turn it off.

Two mitigations are worth knowing:

  • Streamed 2xx response bodies are never captured, even under --all. A streaming success is consumed by the client in real time, so there is no buffered body to record. This is a deliberate reduction in data-at-rest exposure, not an oversight. Error-path bodies are captured.
  • The trace file is set to owner-only permissions on POSIX (chmod 0o600).

File permissions on Windows

On Windows, chmod is a near-no-op. It sets the read-only bit and nothing else — Windows has no POSIX group/other permission model for chmod to express. The trace log, the state file, and the keys file are therefore readable by any account that can reach your home directory unless you restrict them yourself.

Restrict the directory ACL manually with icacls. This applies to ~/.claude/logs/ and ~/.claude/proxy/, and it applies whether or not you use --all, because error text and resolved extra-header values are recorded regardless.

The extra_request_headers field is not gated by --all. Resolved header values — for example a client's per-conversation session identifier — are recorded on every request for a provider that has rules. If you configure such a rule, assume that identifier is in the trace log.

Pruning

Each claude-retry-proxy start removes entries older than 5 days before launching the server. There is no separate rotation or size cap.

Pruning is best-effort and never blocks startup: a log locked by another process is left alone rather than failing the start. Entries are matched by their timestamp; a line the parser cannot read is left alone rather than discarded, so a malformed line persists until it ages out by whatever other means you apply.

Analysis

scripts/analyze_proxy_trace.py aggregates the log per model:

MetricMeaning
Request countEntries in the window
Average retriesRetries per request
Query success rateSuccess treating all retries of one request as a single query
Attempt success rateSuccess counted per upstream attempt
Geometric-mean TTFTTime to first byte, geometric mean
Geometric-mean latencyTotal latency, geometric mean

Two filters keep an outage from dominating the averages: requests with a latency above 30 minutes, and requests at maximum retries that also failed — the signature of a complete upstream outage rather than normal operation.

python scripts/analyze_proxy_trace.py --days 3
python scripts/analyze_proxy_trace.py --days 7 --trace-file /path/to/proxy-trace.jsonl

--days defaults to 3. The geometric mean is used rather than the arithmetic mean because latency distributions are heavily right-skewed: a handful of slow requests would otherwise move the average far away from anything a user experiences.

When writes fail

The trace file is written by a guarded sink that never raises. A failing sink reports the first failure of an episode on stderr immediately, then at most once per 60 seconds while the episode continues, and emits a resumed after N failed write(s) line when writing succeeds again.

Entries written during an outage are lost, not buffered. There is no queue and no replay. The count in the resumed line is the only record of how many entries were dropped — if you need to know what happened during a gap, that number is the whole story.

The failure mode is also the noisiest thing you can do to this log: an unwritable trace directory means every request loses its entry until the condition is fixed. See architecture.html for the full policy.
